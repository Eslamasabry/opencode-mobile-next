# F-Droid feasibility and the `fdroid` build (2026-10-31)

Branch `feat/fdroid-2026-10-31`, from int. Nothing was submitted to F-Droid or
gitlab.com/fdroid; that needs the owner's yes. F-Droid pages and AndCode's repo
were read as data (policy text fetched 2026-10-31).

## 1. Verdict

**Feasible, in two sizes.**

- **Lite (small, mostly done here):** an F-Droid build with no code push, no
  in-app APK update, no ML Kit (gone from all builds, B2), and the prebuilt native binaries removed.
  Remote servers, chat, files, notifications, voice dictation (see risk R2) all
  work. **The built-in Ubuntu / AI Team engine does not** (it needs those
  binaries). Size: about 2 to 3 days more (consent screen, a "not in this
  build" state for built-in Linux, metadata, an MR and its review round trips).
- **Full (large):** also build proot/talloc/shmem from source (AndCode's way,
  Termux build scripts as a srclib, NDK r28/r29) and the Rust AI Team engine
  from `engine/phone` with cargo-ndk, then regenerate
  `aiteam-engine-manifest.json` hashes at build time. Size: 1 to 2 weeks, plus
  the risk that F-Droid's reviewers reject runtime executable downloads.

Precedent is thin: AndCode's merge request (!48005) is still **open**, not
merged, as of today. Treat it as a recipe to copy, not proof of acceptance.

Remaining risks, not blockers yet:

- **R1 Dart, not Shorebird, at runtime.** F-Droid's APK runs on the stock
  engine. The code is the same Dart, but the owner has only ever run the Shorebird
  engine build: smoke the F-Droid APK on the emulator before any submission.
- **R2 sherpa_onnx.** Apache-2.0 / MIT code, but the Android runtime
  (`sherpa_onnx_android_*` on pub.dev) ships prebuilt `libonnxruntime.so` and
  `libsherpa-onnx-*.so`. Pub is not a trusted binary source in the policy (Maven
  Central, Google Maven, JitPack, PyPI wheels, Rust, Go and Node are). The fix, if
  a reviewer objects, is the same conditional-import stub as B2 and a "voice
  dictation unavailable here" state (`supportsVoice`). Whisper model files come
  from huggingface.co on a tap (`Uri.https('huggingface.co', ...)`): disclose as
  `NonFreeNet`-adjacent, or drop.
- **R3 Gradle wrapper / Flutter's own Gradle files** need `scanignore` the usual way.
- **R4 Reproducibility.** Flutter AOT output is mostly deterministic with the same
  toolchain, but nothing here has been compared bit for bit.
- **R5 Maintenance.** The policy wants active maintenance and, for a new app, a
  quality bar ("useful", "unique value"). Fine.

## 4. Anti-features to declare

- **NonFreeNet**: the app is a client for hosted AI services and OpenCode Zen /
  provider sign-ins; its purpose depends on a network service that is not free.
- **NonFreeAdd**: the built-in Ubuntu can install and run proprietary agents (Claude
  Code, Codex). (Same words AndCode used.)
- **NonFreeAssets**: only if the Gemma model ever ships (B5): no.
- **Tracking / Ads / KnownVuln / NoSourceSince**: no.

The draft is `docs/release/fdroiddata-io.github.eslamasabry.opencode_mobile.yml`.

## 5. How Flutter apps are built in fdroiddata

Read from Saber's recipe (`com.adilhanney.saber`, a Flutter app with a flavor) and
the policy text:

- `srclibs: - flutter@<version>` fetches upstream Flutter at a tag; the recipe
  refers to it as `$$flutter$$`. Older recipes vendor it as a submodule and use
  `scanignore` / `scandelete` for Flutter's own Gradle files and `.pub-cache`.
- `prebuild:` runs `flutter config --no-analytics` and `flutter pub get`
  (`PUB_CACHE` set inside the build dir).
- `build:` runs `flutter build apk --release ...`; `output:` names the APK.
  `rm:` strips platform folders F-Droid does not need.
- **Our Flutter**: 3.47.1 from Shorebird's fork (`91f8bd75076e…`). Upstream has the
  tag `3.47.1` (`6655482ec06e…`), so `flutter@3.47.1` works. Proof in §6.
- Updates: `UpdateCheckMode: Tags` reads `version: x.y.z+n` from `pubspec.yaml`
  at tags like `v2.1.0+57`, which is our existing tag form.

## 6. The `fdroid` build, and what it proves

### How it is switched

A Gradle product flavor was **not** used: our release path (`release.sh`,
Shorebird, CI, `vps_build_apk.sh`) all expect `app-release.apk` and
`outputs/mapping/release`; a flavor renames every output and needs
`--flavor` everywhere. The repo's existing pattern for variants is a Gradle
project property (`ocPreview`), so this build uses one too:

```
dart tool/fdroid/prebuild.dart      # drops shorebird_code_push and shorebird.yaml
flutter pub get
flutter build apk --release --dart-define=OC_FDROID=true --android-project-arg=ocFdroid=true
```

- **Dart.** `lib/build_flavor.dart` has `kFdroidBuild` (`OC_FDROID`).
  `PlatformCapabilities` gets `fdroid`; `supportsCodePush` is false when it is
  set, so About shows no update row. A conditional export on `OC_FDROID` swaps
  `shorebird_updater_real.dart` for `_stub.dart`, so the package is not even
  compiled in. Only the "real" file imports it (a test enforces it).
- **Gradle.** `ocFdroid` adds a release manifest overlay that removes
  `REQUEST_INSTALL_PACKAGES`, and (`android/build.gradle.kts`) fails the build,
  naming the dependency, if anything from `com.google.android.gms`,
  `com.google.mlkit` or `com.google.firebase` resolves.

### Proof (VPS, plain Flutter, outside the Shorebird cache)

**Not run yet.** The coordinator paused all VPS builds and tests (overloaded;
the 2.1.0 patch comes first). Upstream Flutter 3.47.1 is already cloned and
precached on the VPS in `~/fdroid-scratch/flutter` (tag `3.47.1`, not the
Shorebird fork). To run the proof when released:

```
tool/fdroid/vps_build.sh 4330     # prebuild, plain-Flutter build, APK audit
```

`tool/fdroid/audit_apk.sh` then lists dex packages for Shorebird, gms, mlkit,
firebase and play, the native libraries, and the permissions, and exits 1 on a
forbidden SDK. Unit-level proof (VPS, Shorebird Flutter): see the test file
`test/fdroid_build_contract_test.dart` and `test/kit_qr_decoder_test.dart`.

## 8. Decisions for the owner

1. **Submit at all, and which size** (Lite now vs Full later). Submitting an MR to
   gitlab.com/fdroid/fdroiddata is yours to approve.
2. **Signing.**
   - *F-Droid signs* (default): simplest, but the F-Droid APK has a different
     certificate than the GitHub/Shorebird build. Same application ID, so a phone
     with one cannot update to the other: uninstall first, losing local data.
   - *Reproducible build with our signature* (`Binaries:` +
     `AllowedAPKSigningKeys`): F-Droid ships our signed APK once its own build
     matches ours byte for byte. Best for users, but needs verified
     reproducibility (R4) and a release-flow step that builds the `fdroid` APK with
     plain Flutter. Never rotate a signer (AGENTS.md).
   - *Different application ID for F-Droid* (e.g. `...opencode_mobile.fdroid`):
     coexists with the GitHub build, no signature clash, two apps.
3. **Update cadence.** F-Droid users never get Shorebird patches: every fix is a
   tagged release. `AutoUpdateMode: Version` + tags `v<name>+<code>` means each
   tag is picked up automatically after F-Droid's own build.
4. **Voice** (R2): keep with a disclosure, or drop from this build.
5. **Disclosures**: you accept NonFreeNet and NonFreeAdd on the listing.
