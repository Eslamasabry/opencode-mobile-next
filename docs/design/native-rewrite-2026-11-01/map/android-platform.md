## 0. Read this first (the twelve things that matter most)

1. **This area is already native.** About 25k lines of Kotlin here are pure Android code with JVM unit tests (46 test classes, Robolectric for widget renders). Most of it carries into the rewrite almost verbatim. What goes away is only the `MethodChannel` glue and the two *headless Flutter engines* (`WidgetActionRuntime`, `ScheduledPromptRuntime`). What must be **re-implemented in Kotlin** is the Dart half: `lib/background/*` (notification wording, widget snapshot builder and redaction, widget action/status runners, live-mode controller), `lib/scheduling/*` (recurrence, store, run engine) and the pure logic in `lib/platform/*` (exit classification, keep-alive advice, connection advice, thermal parsing, native-crash sanitizer, Wi-Fi file share, phone-storage scans).
2. **Component names are a public contract with the OS.** The launcher stores widget providers by `ComponentName`; Quick Settings stores tiles by `ComponentName`; pinned shortcuts store `MainActivity`; WorkManager's database stores worker class names; the user's notification-channel choices are keyed by channel id. A same-package in-place update only keeps placed widgets, tiles, pinned shortcuts and per-channel notification settings if **class names and ids stay identical** (§3, §7, trap T1).
3. **The store is shared with Kotlin through `FlutterSharedPreferences`.** Widgets, the Quick Settings tile, the scheduler and `NativeStrings` read keys written by Dart (`flutter.oc.widgetSessions`, `flutter.oc.profiles`, `flutter.oc.appLocale`, `flutter.oc.keepLiveInBackground`, …). They must keep working while no app UI process exists. The native rewrite needs one process-independent store those surfaces can read; day-1 migration can leave the `flutter.*` file in place (§6).
4. **Privacy is enforced in code at three layers**: Dart redacts before storing (`KitRedact`, `safeWidgetTitle`, `redactForNotification`), Kotlin validates before drawing (`StatusContent.fromMap`, `AlertCopy`, `CodingAlertRequest`), and the lock screen always gets a fixed public version. Never put prompts, tool arguments, paths, server errors or credentials in a notification, widget snapshot, shortcut label, log or WorkManager `Data` (T3).
5. **Every cross-process action is claimed durably before the network boundary and never replayed.** Widget actions use a per-profile claim ledger + 30 s lease; scheduled prompts claim `id:revision:dueAtMs` before dispatch. An uncertain delivery is shown as uncertain and never retried (T5, T6). This invariant is the most expensive thing to lose.
6. **Foreground-service rules shape everything.** `dataSync` has a 6 h/24 h budget on Android 15+ (`onTimeout` must stop within seconds, and a new start then throws); `specialUse` is used for the phone server and setup; `shortService` is used alone for the 30 s widget action on Android 14+; a service started from the background must show its notification within seconds or the app crashes (the `promised/foregroundShown/stopPending` dance in `BuiltinServerService`/`SetupService`) (T8–T10).
7. **One status notification, many owners.** Notification id `4747` is shared by the live-connection service and the phone-server service; the row is only removed when the *last* owner stops. Its wording comes from Dart (`buildNotificationStatus`), is validated/clipped by Kotlin and throttled to one update per 2 s (§4 ANDROID-PLATFORM-05).
8. **The widget family is the biggest piece of UI-in-native code**: 7 provider receivers (only 2 shown in the picker), RemoteViews layouts, a size policy tuned on the owner's ZTE launcher, an overlay activity that hosts a Flutter panel (style, project, steer, voice), and on-demand actions. `previewImage` PNGs are required (the ZTE launcher ignores `previewLayout`) (T14).
9. **Scheduled prompts are an alarm + WorkManager + headless-engine state machine** with a Kotlin-owned compare-and-set store, permanent occurrence claims, receipts, a temporary phone-server lease and a ≤8 min worker budget. The Dart half (`ScheduledPromptRunner`) is ~380 lines of careful protocol work that must move to Kotlin with its test suite (ANDROID-PLATFORM-36..41).
10. **Native strings only exist in English and Arabic** (`R/values`, `R/values-ar`), while the app UI has 7 languages. Native surfaces read the app locale from `flutter.oc.appLocale` on every render and fall back to English for the other five (T16). A rewrite with one shared string source removes this gap.
11. **Nothing in this area may assume unbounded lifetime** (AGENTS.md rule): leases, widget actions, status checks, scheduled workers, team-progress notification (20 min timeout), voice-download notification (15 min timeout), finished-reply alert (1 h timeout) all self-expire.
12. **Unmerged work touches this area** (§14): AppFunctions, in-app APK self-update, Gemma assistant bridge, clipboard image paste, child-process-limit card, `openLocalFile` via FileProvider, Wi-Fi file share links, process budget / agent priority, service-notice gate, F-Droid switches. They are complete branches with tests; decide before the freeze whether they land in Flutter or are ported from the branch.

## 2. Architecture today, and what the rewrite removes

```
Flutter UI / ConnectionController (Dart)                        lib/state/connection/{alerts,surfaces,widgets}.dart
   │  publishes: LiveStatus, NotificationStatus, CodingAlert(show/dismiss), WidgetSessionSnapshot, pinned shortcuts, attention tile
   │  oc/background (+ oc/shortcut, oc/link, oc/share, oc/scheduled_prompts, oc/lifecycle, oc/thermal, oc/network, ...)
Kotlin glue  (MainActivity.configureFlutterEngine registers ~16 channels; NativeChannelReplies wraps replies)
   ├─ BackgroundConnectionService (dataSync FGS, id 4747)  ──┐ shared row (StatusOwners)
   ├─ BuiltinServerService (specialUse FGS, id 4747)  ───────┘
   ├─ Coding alerts (ids 6000+hash, groups 5998/5999)  ← CodingActionReceiver / StatusActionReceiver → back into Dart via MainActivity.backgroundChannel
   ├─ Widgets (RemoteViews) ← read FlutterSharedPreferences only; tap → PendingIntent → BackgroundConnectionService (ACTION_WIDGET_ACTION)
   │      └─ WidgetActionRuntime = headless FlutterEngine running widgetActionMain (oc/widget_action) for ≤30 s
   ├─ ScheduledPromptReceiver/Worker (AlarmManager + WorkManager) → ScheduledPromptRuntime = headless FlutterEngine running scheduledPromptMain
   ├─ Tiles (Attention, Pause), shortcuts, launch extras  → consumed by Dart on start / pushed while running
   └─ Device bridges: network, thermal, lifecycle/exit info, crash store, storage, camera/mic, PDF isolate, TTS, export, SSH signer, Termux
Native persistence: SP "FlutterSharedPreferences" (Dart-written + Kotlin-written keys), SP "oc_background_pause", "oc_background_native", "oc_lifecycle",
                    "camera_permissions", "voice_permissions", files/native-last-crash.properties, files/crash-diagnostics-consent
```

In the rewrite: the app, services, receivers, widgets and workers all run in one native codebase against the same domain client. There is no Flutter engine to start for a widget tap or a scheduled run: a `Worker`/short service runs a coroutine against the shared gateway. `MainActivity.backgroundChannel` (a static used by receivers to reach Dart) becomes a direct call into a process singleton (and, when the process is dead, a cold start of that core inside the service/worker, which costs ~0.25 s instead of an engine boot).

### 4.A Live background connection ("Stay connected") and pause receipts

#### ANDROID-PLATFORM-01 — Process bootstrap and crash-safe start
- **What**: `OcApplication.onCreate` installs `NativeCrashStore(filesDir).install()` *before* any Activity/service so foreground-service start failures are captured. `MainActivity` (singleTop, empty task affinity, `windowSoftInputMode=adjustResize`, handles orientation/locale/layoutDirection/fontScale/density/uiMode itself) re-creates ~16 bridges per engine (`configureFlutterEngine`) and tears them down in `cleanUpFlutterEngine`.
- **Files**: `K/OcApplication.kt`, `K/MainActivity.kt`, `K/NativeChannelReplies.kt`.
- **Notes**: `NativeChannelReplies` guarantees every channel call is answered exactly once; on engine detach all pending replies get `engine_detached`. A reply that throws is never retried. `MainActivity.onResume/onPause` call `BuiltinLinux.setActivityResumed` (feeds idle policy, builtin-linux 25) and `ReadAloudBridge.resume/pause`. `ScheduledPromptScheduler(applicationContext).restore()` runs on every engine configure (re-arms alarms/work). `taskAffinity=""` matters for how Recents/force-stop treats the task on Nubia/Xiaomi (see 44).
- **Rewrite**: keep the manifest attributes; replace the engine lifecycle with normal Activity/ViewModel lifecycle; keep "answer exactly once" as a coroutine contract for any remaining callback API.

#### ANDROID-PLATFORM-02 — Live background mode (foreground service `BackgroundConnectionService`)
- **What**: A user-controlled setting keeps the process alive while the Activity is backgrounded so SSE/terminals stay live and alerts can be posted. The preference is `oc.keepLiveInBackground` (SP key `flutter.oc.keepLiveInBackground`). Enabling asks for `POST_NOTIFICATIONS` (Android 13+, request code 4703), starts the service, and waits **up to 5 s, polling every 50 ms** for Android's start acknowledgement (`MainActivityBackground.awaitBackgroundStart`) — a busy phone can take more than 2 s. Result map: `{enabled, active, backgroundPause, notificationGranted, batteryOptimizationIgnored[, startFailure: refused|receiptUnsaved|ackTimeout]}`.
- **How**: Dart `BackgroundLiveController` (`lib/background/live_background.dart`, 1,003 lines + part `signin_foreground.dart`); Kotlin `BackgroundConnectionService.beginLive` calls `StatusNotification.begin(OWNER_LIVE)`, `startForeground(4747, notif, DATA_SYNC)` inside `runCatching` (Android 15 refuses a dataSync start after the budget: `ForegroundServiceStartNotAllowedException` used to end the app), then `BackgroundPauseStore.confirmedStarted()`; only after that are `liveOwner`, `active` set, the transient-action notification 4748 cancelled, `SessionsWidgetProvider.refreshAll` redrawn and `LivePauseReceiver.setPausedByUser(false)`.
- **Dart behaviour to port**: `restore()` at start: reads `getBackgroundPause`; a durable pause blocks automatic restart; unknown native state fails closed; otherwise `enable`/`getStatus`. `setEnabled` fences concurrent calls with `_pauseRevision` so a late reply never undoes a newer Pause/timeout. `resumeBackground()` only from a visible Resume tap; success requires `backgroundPause.active`. Live status pushes (`updateLiveStatus`) are debounced to **one per 2 s with a trailing push** (`liveStatusDebounce`) and skipped when equal to the last. Unsupported platforms never clear the saved opt-in.
- **Rewrite**: same service type and semantics; `onTimeout(startId, fgsType)` for Android 15+ and the one-arg `onTimeout(startId)` for Android 14's shortService must both exist (see T9).

#### ANDROID-PLATFORM-03 — Pause receipts: why background mode stopped
- **What**: A durable, synchronous receipt in SP `oc_background_pause` (`phase` none|running|paused, `reason`, `at`, plus `taskRemovalHintAt`) survives process death with no Flutter engine. `BackgroundPausePolicy.reconcile` turns "was running, now not" into a reason: `batteryRestricted` (ActivityManager.isBackgroundRestricted), `userStopped` (exit reason 10/11 after the receipt), `appUpdated` (exit 16), `deviceRestarted` (receipt older than boot time −60 s), `timeLimit` (service `onTimeout`), else `interrupted`. `status()` also **turns off the Flutter preference** `flutter.oc.keepLiveInBackground` whenever paused so a stale opt-in cannot restart the service by itself.
- **Files**: `K/BackgroundPauseStore.kt`, `K/BackgroundPauseReceipt.kt` (policy), `lib/domain/background_pause.dart` (`BackgroundPauseState`), `getBackgroundPause` call.
- **Wire**: `{supported, active, paused, reason, at, canResume}`.
- **Notes**: `onTaskRemoved` only records a hint, never classifies a swipe. `onTimeout` writes `timeout()` *before* stopping because neither Flutter nor `onDestroy` is guaranteed to run; it posts the "Paused · Android's background limit" row (`StatusNotification.pausedByAndroid`) and pushes `backgroundServiceTimeout` (`reason: systemTimeout`) to Dart. Starting the service again clears the receipt only after `startForeground` succeeded.
- **Tests**: Dart `background_pause_test.dart`, `background_pause_native_test.dart`, `background_pause_notice_test.dart`, `background_live_test.dart`; Kotlin none for the policy (add one).

#### ANDROID-PLATFORM-04 — Quick Settings tiles
- **Attention tile** (`K/AttentionTileService.kt`): shows "N need you" / "All clear" from SP `flutter.oc.attentionTile` = `{"pendingCount":int,"profileID":str,"updatedAt":ms}`; a count older than **24 h** is ignored (plain "OpenCode"); tap opens `MainActivity` with launch extra `activity` (via `TileServiceCompat.startActivityAndCollapse` + `PendingIntentActivityWrapper`; `unlockAndRun` when locked). Dart writer: `AttentionTileSnapshot` (`lib/background/attention_tile_snapshot.dart`), written when the pending count (permissions + questions + forms) or profile changes, then redraws widgets; `clear()` on disconnect; `clearForProfile` on deletion (returns nothingToClear | cleared | failed).
- **Pause tile** (`K/PauseTileService.kt`): Running → Active; paused-by-user → Inactive and a tap resumes (`LivePauseReceiver.resume` → starts the service; on refusal re-marks paused and opens the app); not enabled in settings → Unavailable. Subtitle strings `pause_tile_on/paused/off`. Uses `startActivityAndCollapse(PendingIntent)` on Android 14+, Intent form below.
- **Native-only prefs**: SP `oc_background_native` key `pausedByUser`.
- **Notes**: Android 10 and below put the state in the label (`tile_label_with_count`). Icon is `ic_launcher_monochrome`. Tiles must keep component names (users add them manually).

### 4.B Notifications

#### ANDROID-PLATFORM-05 — The one status notification (id 4747, channel `opencode_live_connection`)
- **What**: One ongoing, silent (`IMPORTANCE_LOW`, no badge) row for everything OpenCode is doing. Situations, highest wins (Dart `buildNotificationStatus`, `lib/background/notification_status.dart`, 511 lines): **needs_you** → **paused_android** (dataSync cap) → **reconnecting** → **working** (one chat: title = live line, text = chat title + "5 of 6" tasks, subText = project · elapsed · server, progress bar only when tasks exist, actions Open + Stop the reply) / **several_working** (inbox lines, `notificationStatusMaxLines=2` then "+N more") → **paused_hot** → **waiting** (provider retry: "Tries again at 1:12", Open + Stop the reply) → **paused_idle** (action Start) → **setup** ("step 4 of 5", percent) → **idle/ready** ("Last reply 12 min ago · title", actions New chat + Stop OpenCode when the phone server runs). The server name appears only when more than one server is live.
- **Kotlin**: `K/StatusNotification.kt` (owner set + wording + throttle), `K/StatusNotificationModel.kt` (pure: `StatusKind` wire names must match Dart, `StatusAction` open|stop_reply|start|new_chat|stop_server, `StatusContent.fromMap` clamps: title/text/line ≤240 chars, ≤4 lines, ≤3 actions, progress 0..100, malformed map refused so a bad push never replaces a good one; `StatusOwners`; `StatusThrottle` = one post per **2000 ms**, only when content changed, trailing post of newest content), `K/StatusNotificationRenderer.kt` (builder, `setOnlyAlertOnce`, `CATEGORY_SERVICE`, `VISIBILITY_PRIVATE`, public version with count-only `publicTitle`, InboxStyle for lines, `setProgress` only for a real fraction).
- **Ownership**: `begin(owner)` records the owner, clears the stale setup result row (4099), forces the content. `end(owner)` returns true only for the last owner; otherwise the row is re-posted with what remains true (`STOP_FOREGROUND_DETACH` for the service that is leaving). With no Dart wording the phone server alone shows a fallback ("Ready", New chat + Stop OpenCode, subText "On this phone").
- **Android 16 QPR1+**: `setRequestPromotedOngoing(true)` + `setShortCriticalText(chip)` for WORKING/SEVERAL_WORKING/NEEDS_YOU, gated by `SDK_INT >= BAKLAVA && SDK_INT_FULL >= BAKLAVA_1`; needs `POST_PROMOTED_NOTIFICATIONS`. Chip text comes from plurals `native_chip_running/pending`; count is parsed from the leading digits of the title.
- **Status actions**: Open/Start/New chat are activity PendingIntents (request codes 0/10/11/12; New chat sends launch extra `new_task`); Stop the reply is a broadcast to `StatusActionReceiver` with `opencode://status/stop_reply`, extras action + session id → Dart `statusAction` (handled → done; else the app opens). Stop OpenCode is `BuiltinServerService.stopIntent` (`getService`, action `stop`).
- **Notes**: Dart pushes via `updateLiveStatus {runningCount, pendingCount, title, detail, status:{…}}`; with no service running the wording is remembered for the next start. `refreshNativeLocale` re-reads fixed copy even when content is unchanged.
- **Tests**: Kotlin `StatusNotificationModelTest`; Dart `notification_status_test.dart`, `notification_status_controller_test.dart`, `live_status_test.dart`, `connection_status_presentation_test.dart`.

#### ANDROID-PLATFORM-06 — Alerts ("moments"): needs you, finished, stopped, quota, check-in, test
- **Channels**: `opencode_coding_action` (HIGH, "requests"), `opencode_coding_status` (DEFAULT), `opencode_coding_action_quiet` (LOW, same requests with no sound/heads-up during quiet hours), `opencode_team_progress` (LOW). All lock-screen `VISIBILITY_PRIVATE`.
- **Kinds** (`CodingAlertKind`, wire values): `permission`, `question`, `complete`, `error`, `quota`, `quota_reset`, `checkin`, `test`, `team_decision`, `team_run_failed`, `team_review`, `team_completed`, `team_progress`.
- **Posting** (`BackgroundConnectionService.showCodingAlert`, request `CodingAlertRequest`): valid only with non-blank `sessionID` and `key`; quota kinds require `sessionID=="quota"`, a profile id and a 64-hex `monitorToken`. Notification id = `6000 + (key.hashCode() & 0x0fffffff)`; `key` is Dart's dedupe key (`input:<profile>:<session>`, `status:<profile>:<session>`, `team:<profile>:gate:<gate>`, `team:<profile>:run:<run>`). Refused (returns `shown:false`) when notifications are off or the channel importance is NONE. Agent name only if it matches `^[A-Za-z0-9 .-]{1,32}$` else "OpenCode".
- **Copy**: the **lock screen** gets fixed public words (`native_public_needs_you`, `native_public_finished`, `native_status_public_stopped`); the **shade** gets the person's words, built by `AlertCopy.of`: permission → title "Run npm install?" / "Edit settings.dart?" / "Read …?" / "Open folder …?" (`askAction` run|edit|read|folder + masked `askTarget` ≤40) with the exact command/path (≤140) in the body, else "Allow OpenCode to continue?"; question → its words ≤80 as the title and ≤3 short choices (each ≤24, unique) as `a · b · c`; complete → "<chat title>" + first reply line; error → "<chat> stopped" + plain reason from token `auth|context|length|filter|model|other` (never raw error text). `subtext` ("MacBook · api-server", ≤80) rides as sub-text.
- **Buttons** (`AlertButtons.plan`): at most two. Permission whose command/file is readable in the body: **Allow once** (`setAuthenticationRequired(true)` on Android 12+, i.e. phone must be unlocked) and **Reject**. "Always allow" is never offered. Everything else (question, form, permission without a readable target) has only **Open**. Legacy RemoteInput Reply and `option*` decisions are still accepted by `CodingActionReceiver` for old alerts.
- **Groups**: `opencode_needs_you` (permission, question, team_decision) and `opencode_finished` (complete); a summary (id 5998 / 5999, InboxStyle, up to 5 lines, plural `native_group_need_you/finished`) appears only with ≥2 children and is removed with the last. `complete` has `setTimeoutAfter(1 h)`. `team_progress` is ongoing, silent, `setTimeoutAfter(20 min)`, own public version, channel `opencode_team_progress`. `setOnlyAlertOnce` is true except quota kinds.
- **Open routing**: body tap / Open button → `MainActivity` with extras kind, sessionID, profileID, monitorToken (`FLAG_ACTIVITY_CLEAR_TOP|SINGLE_TOP`), captured by `LaunchActivityBridge.captureCodingAlertOpen` (extras removed, so a configuration change cannot replay it) and fetched by Dart `consumeCodingAlertOpen`. Widget Reply sets `oc.widgetReply` so the composer is focused.
- **Dart decision rules** (`lib/state/connection/alerts.dart`, state-data 31): alerts post only when keep-live is on, the app was backgrounded, notification permission is granted and the server's alerts are on. Quiet hours do not stop requests/failures (they post silently via the quiet channel); only finished-reply alerts wait for the morning. Finished alerts skip sub-agent sessions. ### 4.E Scheduled prompts

(Contract: `docs/design/scheduled-prompts-contract-2026-10-15.md`. Tests: Dart `scheduled_prompt_*_test.dart` (9 files), Kotlin `ScheduledPromptPolicyTest`, `ScheduledPromptStoreTest`, `ScheduledPromptRecoveryTest`.)

#### ANDROID-PLATFORM-35 — Model and recurrence
- `ScheduledPrompt{id, profileId, profileFingerprint, prompt≤32000, projectPath≤4096, workspace?, sessionId?(null = new conversation each run), agent?, modelProviderId?+modelId? (both or neither), recurrence, missedPolicy catchUp|skip, enabled, nextRunAt?, createdAt, revision}`; ids match `[a-zA-Z0-9_-]{1,128}`. Recurrence kinds: `once(at)`, `daily(hour,minute)` (wall clock, DST-safe, added in `6be75670b`), `weekdays(hour,minute)`, `interval(hours 1..168, anchor)` (absolute UTC anchor, never drifts). `nextScheduledOccurrence` is implemented **twice** (Dart `recurrence.dart`, Kotlin `ScheduledPromptPolicy.nextDaily/nextWeekday` + `ScheduledPromptRecovery.next`) and must stay identical; calendar construction (not +24 h) preserves wall clock across DST. Late = more than **15 min** after due; `scheduledPromptDue` collapses all missed occurrences into one catch-up or one skipped record; no burst replay. Occurrence id `id:revision:dueAtMs`. Digest (`__digest`): optional morning summary at hour:minute with `lastDeliveredAt` claim.

#### ANDROID-PLATFORM-36 — Native-owned compare-and-set store
- Single versioned envelope per profile at SP key `flutter.oc.scheduledPrompts.<profileId>` (`{schemaVersion:1, schedules[≤100], runs[≤500], digest}`, ≤4 MiB). Dart `ScheduledPromptStore` uses `readStore`/`casStore` over `oc/scheduled_prompts` (20 optimistic retries; `storage_busy` after). Kotlin `ScheduledPromptStore` serializes under one JVM lock shared by UI and headless engines, **rejects reads/writes when the profile is not in `flutter.oc.profiles` or is tombstoned** (`flutter.oc.scheduleDeleted.<profile>`=true), and keeps companion keys: index `flutter.oc.scheduleIndex.<profile>` (`[{id,revision,dueAtMs}]`, derived from the latest envelope + enabled digest), claims `flutter.oc.scheduleClaims.<profile>` (`{<occurrence>:{at,finished}}`, trimmed to 256), receipts `flutter.oc.scheduleReceipts.<profile>` (≤256 failed-run receipts the UI merges into history), phone lease `flutter.oc.schedulePhoneLease.<profile>`.
- Corrupt/unknown schema is an admission failure (`storage_corrupt`), never empty success. Delete removes visible history but **claims stay fenced** until profile deletion so a delayed worker can't repeat a removed run. Errors are fixed codes (`schedule_limit, stale_schedule, schedule_missing, schedule_expired, storage_limit, invalid_run_transition, history_limit, invalid_profile, unsupported`).
- Rewrite note: this is a durable job queue with exactly-once-ish semantics; implement as a real database (Room/SQLDelight) with the same transactional rules, plus a migration from the SP envelopes (keep JSON schema version 1 readable).

#### ANDROID-PLATFORM-37 — Arming: AlarmManager + WorkManager
- `ScheduledPromptScheduler.replace(profile)` re-derives the index from the envelope (stale UI payloads must never undo a worker advance), cancels removed entries and `arm`s current ones: `enqueue` unique work `oc.schedule.<profile>.<occurrence>.fallback` (`KEEP`, initial delay = due − now, tag `oc.schedule.<profile>`) **and**, when `canScheduleExactAlarms()` (always true below Android 12) and due is in the future, `setExactAndAllowWhileIdle(RTC_WAKEUP)` with a `PendingIntent.getBroadcast` (`oc-schedule://<profile>/<occurrence>`). The alarm's own work is `….alarm` and is **expedited on Android 12+** (`RUN_AS_NON_EXPEDITED_WORK_REQUEST`) only for a real alarm broadcast with zero delay and not for restore or digest (restore work occupying the alarm name would suppress a later expedited request through `KEEP`). Alarm and fallback are mutually exclusive through the durable claim, not by cancelling a running worker.
- `ScheduledPromptReceiver`: `FIRE` → enqueue from alarm; BOOT_COMPLETED / MY_PACKAGE_REPLACED / exact-alarm permission change → `restore()`; TIME_SET / TIMEZONE_CHANGED → `restore(rebaseCalendar=true)` which recomputes future daily/weekday occurrences (overdue ones are preserved for the catch-up/skip policy). `goAsync` + a thread. Orphan entries whose profile no longer exists are cancelled.
- `requestExactAlarm` opens `ACTION_REQUEST_SCHEDULE_EXACT_ALARM` only from an Activity context and only on an explicit tap. `status` → `{supported, exactAllowed, batteryExempt, notificationsAllowed}`. Without exact access Android schedules approximately; force-stop prevents execution until the app is opened.

#### ANDROID-PLATFORM-38 — Worker execution and settlement
- `ScheduledPromptWorker` (`Worker`, never retried after claim because transport failure can follow accepted delivery): global `Semaphore(1)` gate; **worker budget 480 s**, **Dart budget 420 s**, minimum Dart window 15 s (`Result.retry()` before claim if less remains). Steps: not due yet (clock rollback) → re-arm with `replacePending` and stop; `store.claim(entry)` → `new|recover|duplicate|stale` (`recover` = a prior claim exists unfinished: only writes interrupted history, never sends); start `ScheduledPromptRuntime` (headless FlutterEngine, `scheduledPromptMain`, `execute` args `{profileId, scheduleId, revision, scheduledAtMs, deadlineEpochMs, recoveryOnly, manual}`); wait; if Dart answers `skipped/not_due` while the entry is still in the future, un-claim a fresh attempt (`deferEarlyOccurrence`) and re-arm; else `settle` (claim finished; if the occurrence is still current — i.e. Dart didn't advance it — write an `interrupted` (or Dart-reported) failure into the envelope via `ScheduledPromptRecovery.repair` and stage a receipt) and show a notification.
- **Run now** (`manual:true`, unique work `….manual`): same worker and Dart runner, no claim, no settlement, never moves `nextRunAt`.
- **Notifications** (`ScheduledPromptNotifications`, channel `opencode_scheduled_prompts` DEFAULT; tag = work name): title = conversation title (≤80, secret-like tokens replaced by `…`) for a finished run, generic otherwise (lock screen always generic); body = first reply line (≤100) / "started" / skipped / plain failure reason from code (`needs_you|permission_required`, `auth_required`, `agent_failed`, `timeout|uncertain_delivery|interrupted`, else unavailable); quiet skips (`stale_target`, `not_due`, `disabled`) post nothing; digest shows counts and posts only if >0. Each notification has **its own group key (the work name)**: Android auto-grouped it with the phone server's ongoing row and a tap on the collapsed row started the app without the run's extras (`553240501`). Failed runs add an Open action. Tap → `MainActivity` with data `oc-schedule-open://<profile>/<occurrence>` and extras `scheduledProfileId, scheduledPromptId (empty for digest), scheduledSessionId`, captured by `ScheduledPromptChannel.captureOpen` (extras removed) and pulled by Dart `consumeOpen`/`openAvailable`.
- Dart open routing (`open_route.dart` `resolveScheduledOpen`): conversation if the run reached one and the server fingerprint still matches; else the schedule's history; digest → first schedule's history; deleted schedule or changed server → nothing. Held until startup connection settles (or 30 s), then retried on connection change (`23c851fc8`).

#### ANDROID-PLATFORM-39 — Dart run engine (to port)
- `executeScheduledPrompt` (`lib/scheduling/entrypoint.dart`, 258 lines): validates stale target (`revision`, `nextRunAt`), `scheduledPromptDue`, records a `running` run **before** crossing the network, creates/looks up the run, calls `ScheduledPromptRunner.execute`, records the final run once, `advanceOccurrence(expected, next)` only for the exact claimed occurrence (a stale worker never revives a removed schedule or overwrites an edit/pause), re-syncs the native index.
- `ScheduledPromptRunner.execute` (`runner.dart`, 378 lines): deadline-aware; `guard()` before/after every read (fresh `isCurrent`: enabled ∧ same revision ∧ same `nextRunAt`); profile fingerprint (`scheduledProfileFingerprint`) must equal the saved one; opens a connection (`ScheduledAgentConnection.open`, unsupported: transient transports, non-v2 OpenCode; `auth_required` for password re-entry/missing Codex token; `cleartext_unconfirmed`; certificate pin only if the pin origin equals the base origin); health loop up to **90 s** only when this run started the phone server (2 s steps); `capabilities.scheduledPrompts` else `unsupported`; existing session: must be in `schedule.projectPath` (else `wrong_project`), persist the route (`onSessionCreated`) **before** dispatch, snapshot message ids, skip as `busy` if status ≠ idle; new session: `createSelectedSession` (agent/model) counts as `dispatched` (never repeated after an ambiguous response); apply a captured agent/model by **field-patching** setters (never write back a whole stale session), re-checking idle before each; final idle check, then `promptAsync`; after acceptance follow the run (2 s poll) until a new assistant reply is done and status idle → `ran` (+ title and ≤100-char reply line), `agent_failed`, or `needs_you` (pending permission or form). A remote run that outlives the deadline is still `ran` ("started"); a phone-started server must finish before its lease releases. Error mapping: `ScheduledRunFailure(reason)`, `uncertain_delivery` if dispatched but not accepted, `timeout`, ApiException → `auth_required|certificate_changed|certificate_invalid|cleartext_unconfirmed|unavailable`.
- Run statuses `running|ran|failed|skipped` ("ran" means *accepted*, not that the AI task succeeded; UI says "Started"). Fixed error codes only (`^[a-z][a-z0-9_]{0,79}$`).

#### ANDROID-PLATFORM-40 — Temporary phone-server lease
- When the profile's server URL is the managed in-app Ubuntu server (`BuiltinLinux.managesServerUrl`) the run calls `acquirePhoneServer{profileId, runtime:'openCode2', password, deadlineEpochMs}`: requires installed runtime, not installing/protected, no other active lease, password equal to `root/.oc-builtin/server.password`; if the server already runs it returns `{started:false, token:''}` and is not adopted; otherwise launches `opencode2 serve` through the restoration recipe wrapped in `timeout --signal=TERM --kill-after=5s <budget>s` (Ubuntu bounds the child even if Android dies), commits an admission marker `flutter.oc.schedulePhoneLease.<profile>` (token, boot count, `startedElapsed`, `deadlineElapsed`, `deadlineWall`; window = budget + 66 s launch slack, max `DART_BUDGET_MS+66 s`) *before* launch, and starts a daemon watchdog thread. `activePhoneLease` (read-only) blocks interactive sends (composer, queue, GenUI) while a scheduled run owns the server, using boot id + monotonic deadline (survives wall-clock changes; reboot ⇒ not active). `releasePhoneServer(token)` stops only that exact tracked tree (never by port or pattern). The bridge tracks tokens per instance and `releaseAll()` on close. See builtin-linux 27.

## 11. Hard-won behaviours a rewrite must not lose

Numbered traps (T-ids); commit ids from `git log` of this tree.

- **T1 Component/channel/key stability.** Placed widgets, QS tiles, pinned shortcuts, WorkManager rows and user channel settings are keyed by class name/id. Keep all `io.github.eslamasabry.opencode_mobile.*` component class names listed in §3, all channel ids in §7, shortcut ids, and the activity class `MainActivity`. A mismatch silently removes the user's widgets/tiles.
- **T2 Alarms die on update.** AlarmManager alarms are removed when the package is replaced: `ScheduledPromptReceiver` handles `MY_PACKAGE_REPLACED` and re-arms from the envelope. Keep that, and keep the exact-alarm-permission-state-changed re-arm.
- **T3 No content on the lock screen or in logs.** Public versions are count/fixed words; the shade shows the person's own words but masked (`redactForNotification`). Raw errors never become copy: error alerts use reason tokens. Crash store keeps no messages/frames/paths. Scheduled-run titles mask secret-like tokens (`sk-…, ghp, xox, AIza`).
- **T4 Allow once needs an unlocked phone; "Always allow" never from a notification; never allow what you cannot read** (no command in the body ⇒ Open only). Same rule on widgets.
- **T5 Claim before the network, never replay.** Widget ledger (128 ids) and schedule claims (256) are written with `commit()` before dispatch; a surviving claim means *uncertain*, shown as such; only definite `rejected` releases it. Timeout after dispatch = `uncertain`, not failure.
- **T6 Scheduled runs never queue/steer/interrupt and never auto-approve.** Busy conversation ⇒ skipped; permission requested ⇒ failed `needs_you`; no atomic "send only if idle" exists on servers so a competing client stays a race (documented).
- **T7 Stale writers must not win.** Index is derived from the latest CAS envelope under the lock; `advanceOccurrence` compares revision + `nextRunAt` as *instants* (fix `eac22a34b`: UTC JSON vs local `DateTime` identity); a foreground widget update beats an old action patch; `invalidateConnection` doesn't mark old snapshots connected.
- **T8 A promised foreground service must show its notification.** `startForegroundService` from the background obliges `startForeground` within seconds; stopping first crashes the app. `BuiltinServerService` and `SetupService` track `promised`, `foregroundShown`, `stopPending`. Every `onStartCommand` path (including malformed widget taps) meets the contract.
- **T9 Timeout callbacks.** Android 15 `onTimeout(startId, fgsType)` and Android 14 shortService `onTimeout(startId)` both implemented; stop in seconds; commit the pause receipt first; never reuse an old pause as a restart permission. A refused dataSync start (budget spent) must not crash the app (fix in `84ec04d90`).
- **T10 Sign-in during a pause is allowed, live mode isn't** (`84ec04d90`, device-found: "Code: sign-in-lost").
- **T11 Shared status row ownership.** Stop one owner without removing the row while the other runs; re-post what remains true.
- **T12 Notification rate limit.** Android drops updates beyond ~5/s; app throttles to 1 per 2 s; the perf audit measured `BuiltinServerService lastStartId=804` and 3015 updates (755 refused) in 1 h 50 min — each start re-posted the row (fix `5e5c8ab42`, `ServiceNoticeGate`, in-flight).
- **T13 Scheduled notification grouping.** Give each run its own group key; auto-grouping with the phone server's ongoing row broke taps (`553240501`).
- **T14 ZTE/MiFavor launcher.** Ignores `previewLayout` → use `previewImage`; mis-resolves size-keyed `RemoteViews` maps → render once for the current size (`851f9cc70`); a stopped chronometer's spoken words are ignored by Android (`d060c2e83`). Test widget changes on that launcher, not only a Pixel emulator.
- **T15 Widget placed before any data.** Configure must open with an empty identity and Save under the `_device` key; cancelling makes the launcher drop the widget (`3c12a0e43`, `21b606ff1`).
- **T16 Native locale.** Services run without UI: read the stored app locale per render; only en/ar resources exist natively today.
- **T17 Pending-intent uniqueness.** PendingIntents that differ only in extras are the same PendingIntent: use distinct request codes and `data` URIs per decision/widget/line (setup 2 vs 3, widgets `opencode-widget://…/<id>`, alerts `opencode://coding-alert/<key>/<decision>`). `FLAG_IMMUTABLE` everywhere except where the system must fill in (installer, in-flight).
- **T18 Launch extras are consumed once.** Remove extras (`oc.shortcut`, coding-alert extras, scheduled-open extras, share text, link) after capture so rotation or config change never replays; consume rejected links too.
- **T19 Cold-start races.** Live pushes can arrive while the cold-start consume is in flight: generation counters keep the newer value. Scheduled-run open waits for the startup connection (30 s cap) then re-checks on every change (`23c851fc8`).
- **T20 Android background-start exemptions.** A widget interaction may start a foreground service directly (`PendingIntent.getForegroundService`, no trampoline Activity); a tile click may start the activity only via `startActivityAndCollapse`.
- **T21 Exit info quirks.** Subreason isn't public API (parse `toString` or reflect `getSubReason`); descriptions can contain exception text and must never be forwarded; read the retained buffer with `maxNum=0` then filter; some phones force-stop on swipe and run none of our code, so services-running state is persisted with `commit()` on every change.
- **T22 Thermal headroom** returns NaN when polled faster than ~1/s: poll ≤ every 30 s.
- **T23 TTS/mic arbitration.** TTS must stop before the recorder starts; guard window 10 s; audio focus loss and output removal cancel; text never logged.
- **T24 PDF parsing is untrusted**: isolated UID, FDs not paths, unlinked temp files, kill the process after each request.
- **T25 Keystore-held SSH key never exported**; agent socket checked for uid, dir mode 0700, path shape.
- **T26 Network callbacks.** Use callback arguments, not synchronous capability queries; ignore a late `onLost` for a replaced default.
- **T27 R8.** Keep `WorkDatabase_Impl()` constructor and the worker constructors; release shrinker removed them and crashed start-up (APK 900055).
- **T28 Cleartext config is intentionally permissive; enforcement is in code** — porting must not "fix" it to HTTPS-only (it would break LAN/Tailscale servers) nor drop the consent/pin gates.
- **T29 Time changes.** TIME_SET/TIMEZONE_CHANGED rebase future wall-clock schedules but preserve overdue occurrences; a backward clock re-arms an unclaimed early worker with `REPLACE`; "not_due" from Dart un-claims a fresh attempt.
- **T30 Memory-resident state is disposable.** `MainActivity.backgroundChannel`, widget pending flag, lease tokens are process-local; durable truth is on disk. Expect the process to die between any two steps.

## 12. Performance notes

- Cold start: native demo ~0.25 s vs Flutter ~0.4 s; headless Flutter engines for widget taps/schedules cost an engine boot each (bounded by the 30 s lease / 420 s Dart window). The native rewrite removes this.
- Widget redraws are the hot path: `refreshAll` re-renders every placed provider; renders read SP and parse JSON each time. Snapshot writes are skipped when unchanged and serialized; masking cost was 22% of main thread during streaming before the cache. Keep an in-memory parsed snapshot with a version stamp in the rewrite and redraw only on changed bytes.
- Live status: ≤1 push/2 s from Dart plus ≤1 post/2 s in Kotlin (double throttle; the Kotlin one is authoritative because a service start bypasses Dart).
- Notification churn: avoid re-posting the shared row for every child-process-set change (`ServiceNoticeGate`).
- WorkManager: all scheduled work is one-off, bounded (<10 min), no continuous dataSync assumption; a global `Semaphore(1)` serializes headless runs.
- Thermal: one status listener for the process; headroom poll 30 s only while Dart listens.
- Network: one default-network callback while listened to.
- PDF: ≤2 MP output, ≤10 MiB; one request at a time; 12 s cap.
- Read aloud: non-blocking `AudioTrack` writes on one writer thread with 15 ms backoff; chunks ≤3000 chars.
- Android 17: RemoteViews bitmap budget `6*w*h` (targeting 37).

## 15. Risks

1. **R1 Identity drift on in-place update** (T1): different package name for classes ⇒ widgets/tiles/shortcuts/WorkManager break silently. Highest-impact, easiest to test: install the Flutter release, place Conversations + Status widgets, both tiles, a pinned shortcut, a schedule and a notification-channel customization; update to the native APK; verify all survive.
2. **R2 Fingerprint algorithm** (§58): if the Kotlin JSON canonicalization differs from Dart's `jsonEncode(profile.toJson()..remove('name'))`, every schedule, widget target and follow-up ticket goes stale. Either keep the exact byte format, or recompute and rewrite stored fingerprints during migration.
3. **R3 Dual implementation of recurrence/recovery** (Dart + Kotlin today). A rewrite should have exactly one implementation and golden tests across DST boundaries (both `nextDaily`/`nextWeekday` and interval).
4. **R4 Foreground-service budget and OEM kills.** dataSync 6 h/24 h, specialUse timeouts, OEM swipe-kill (Nubia/Xiaomi/Oppo/Vivo/Huawei/Samsung) are unfixable in code; the Keep-running guidance and recovery flows are product features, not polish.
5. **R5 Shorebird ends.** Native fixes need a full APK; the in-app update path (§14) must land with the first native release and be signed with key `1DE5BF08…D60C`; any native-only crash on first launch can't be hot-patched.
6. **R6 Widget launcher variance.** The ZTE launcher is the owner's daily surface; keep XML RemoteViews layouts + `previewImage` PNGs on day 1. Glance 1.1.1 wraps RemoteViews and does not remove the size-map and preview issues; its newer line is alpha (July 2026). Re-evaluate after the migration.
7. **R7 Android 17 targeting.** Targeting 37 enforces the RemoteViews bitmap budget, stricter background-activity-launch rules for `IntentSender`, background-audio rules (read-aloud is foreground-only, so safe). `compileSdk 37` is already required.
8. **R8 Headless-engine removal changes failure modes.** Today a crash inside Dart can't take down the widget service; in-process Kotlin coroutines can. Keep the 30 s/420 s watchdogs and isolate with `try/catch` + `onTimeout`.
9. **R9 Exactly-once semantics for scheduled prompts** are subtle (claims, receipts, recovery); do not simplify into "WorkManager unique work". The test suite (Dart 9 files + Kotlin 3) is the spec.
10. **R10 Localization gap** (T16): moving native copy to a shared 7-language table changes visible strings in widgets/notifications; ensure Arabic RTL widgets (mirrored layouts, bidi isolates for titles) are checked on the launcher.
11. **R11 Secrets in headless contexts.** Widget/schedule runners load the saved profile and secret via `ProfileStore.loadForWidgetAction` (reload prefs, restore cleartext consent + certificate pin + secret). The native secret store must be readable from a worker with no UI and must still fail closed on an undecryptable entry (state-data 2.2).
12. **R12 Hidden dependency on Termux's JNI** (`PtyAccess` forwards to a package-private class) — pinned `v0.118.3` from JitPack; verify the dependency still resolves on the VPS.
