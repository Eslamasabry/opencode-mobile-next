# Command receipts: feasibility and evidence

Research date: 2026-10-02. Finish line: identify supported durable admission lookups so an uncertain request can be checked without another send. Non-goal: implement a host service, public remote access, UI, or claim exactly-once execution for every server mutation.

Public source was downloaded read-only into `/tmp/receipts-*`; no server was started and no provider credentials were used. Remote runtime access remains Tailscale or an SSH tunnel. Capability conclusions below apply to the inspected versions, not all future versions.

## Matrix

“Confirmed” means the server admitted/stored this command, **not** that a model turn or tool finished. No inspected OpenCode API has a general command-receipt lookup or documented general `Idempotency-Key` header.

| Server/version | Mutation and client identity | Lookup after a lost response | Execution/admission guarantee and safe client behavior |
|---|---|---|---|
| OpenCode 1 `opencode-ai@1.18.32` | Prompt `/session/{id}/message` and `/prompt_async` accept `messageID`. | `GET /session/{sessionID}/message/{messageID}` returns the user message and parts. | **Lookup supported; repost unsafe.** A repeated prompt rebuilds the user message, emits an upsert, and invokes the agent loop. Preserve original ID and only check it after uncertainty; a 404 does not prove the first request never ran. [OC1-A], [OC1-B], [OC1-C]. |
| OpenCode 1 `1.18.32` | Session create has no client session ID in its public input. Permission replies/revert are operation/resource addressed, not client command addressed. | Session/permission/message refetch can show current state, without identifying the exact lost command. | Keep existing refetch reconciliation; never infer an exact receipt from a matching title/prompt. Session create cannot be safely retried by a command ID. [OC1-D]. |
| OpenCode 2 stable `@opencode/cli@2.0.10` | Session create accepts `id` (`ses_…`); prompt accepts `id` (`msg_…`). | `GET /api/session/{sessionID}`; prompt first checks `GET /api/session/{sessionID}/message/{messageID}`, then the session inbox for the same ID. | **Durable identity supported.** Create returns the stored session; concurrent create race returns the existing projection. Prompt reconciles existing inbox **or promoted user message** before preparing another payload. First admission wins. This slice still uses lookup-only Retry. [OC2-A], [OC2-B], [OC2-C]. |

| Paseo current source `bd3986d…` (cheap check, not `0.9.2` proof) | `send_agent_message_request` accepts `messageId` alongside correlation `requestId`. | Repeating same request consults a durable receipt; timeline user message also carries optional `messageId`. An absent lookup remains **uncertain**. Original admission may still be in flight, an inbox item may have been cancelled, history may have been deleted, the host may have changed, or storage may have rolled back. Do not convert absence into permission to send again. OpenCode's identities are not payload hashes; generate once and bind the ID to an immutable local command. A command must retain profile, server authority, directory, session and originating tab context.

## MonoCode: actual code lessons, not a service dependency

Inspected MIT revision [`1e97594ddf6f40aa24671f7fa09f2048deb1d5eb`](https://github.com/hardbeat920/monocode/tree/1e97594ddf6f40aa24671f7fa09f2048deb1d5eb), [license](https://github.com/hardbeat920/monocode/blob/1e97594ddf6f40aa24671f7fa09f2048deb1d5eb/LICENSE). The README links remote access as experimental; [remote-access.md](https://github.com/hardbeat920/monocode/blob/1e97594ddf6f40aa24671f7fa09f2048deb1d5eb/docs/remote-access.md) describes loopback host with SSH forwarding, surviving disconnects, and tab-owned pending requests.

- [`host/engine.ts:414–425, 693–711`](https://github.com/hardbeat920/monocode/blob/1e97594ddf6f40aa24671f7fa09f2048deb1d5eb/host/engine.ts#L414-L425) hashes the entire command, returns an earlier receipt, and stores state plus receipt transactionally before invoking the provider effect. Its comment explicitly distinguishes host acceptance from provider completion.
- [`host/store.ts:238–249`](https://github.com/hardbeat920/monocode/blob/1e97594ddf6f40aa24671f7fa09f2048deb1d5eb/host/store.ts#L238-L249) refuses reuse with a changed payload; receipt IDs are database primary keys.
- [`connections/model/connections.ts:83–151`](https://github.com/hardbeat920/monocode/blob/1e97594ddf6f40aa24671f7fa09f2048deb1d5eb/src/features/connections/model/connections.ts#L83-L151) persists each command separately before dispatch, with project/environment scope and shell/tab ownership. Persistence failure prevents sending.
- [`connections/ui/RemoteSession.tsx:560–583`](https://github.com/hardbeat920/monocode/blob/1e97594ddf6f40aa24671f7fa09f2048deb1d5eb/src/features/connections/ui/RemoteSession.tsx#L560-L583) writes pending first, keeps original ID, and guards a late response with a binding version. [`1024–1036`](https://github.com/hardbeat920/monocode/blob/1e97594ddf6f40aa24671f7fa09f2048deb1d5eb/src/features/connections/ui/RemoteSession.tsx#L1024-L1036) actually dispatches the same pending command again: host receipt interception makes that safe. OpenCode lookup-only Retry must not copy this dispatch behavior indiscriminately.
- Actual `src/features/sessions/model/handoffTurn.ts:23–60` and `session.ts:464–466` were read: local provider cancellation/question request IDs are process-local and are not durable receipt IDs. This reinforces keeping receipt ownership independent of volatile UI/execution state.

No MonoCode host is added. Reuse the journal-before-send, immutable identity, origin binding and acceptance/completion distinction in our client. Our allowed transport policy is narrower than MonoCode's documented optional HTTPS proxy.

## Version and authentication boundaries

OpenCode 1 uses the current profile's existing transport/auth/directory. OpenCode 2 beta and stable use the current profile's existing HTTP Basic authentication and `/api` paths, with dialect translation already in `lib/api2/dialect.dart`. Beta `GET /api/health` and stable `GET /api/info` identify the protocol generation; a flavor alone is not version proof. Do not probe provider config for receipts, log authorization or request bodies, install a helper service, or create new remote access.

The SDK contract is an older pinned snapshot `f12e14cf…`, documented in `contracts/README.md`, not proof that every `1.18.x` has all current behavior. The beta contract is the captured `18600` API; exact core package source below corroborates its create/prompt admission implementation. Versions outside this evidence retain conservative lookup-only/refetch behavior; do not advertise universal execution idempotency.

## Decision for this backend slice

Enable exact admission lookup for OpenCode prompts with a client-generated message ID. OpenCode 2 creation with a client-generated session ID is supported by `SessionCreationReceipts`; the session-create owner must wire that backend seam into the existing flow. An uncertain command is never dispatched again by Retry. Unsupported operations keep existing refetch behavior; missing matches stay uncertain. A disconnected or crashed client reloads the durable journal and checks the original profile/server scope. Broader operation coverage, Codex/Paseo adapters and any explicit “send as a new request” UI need separate owner decisions and evidence.
