# ACP primary-source evidence — 2026-10-02

Finish line: establish the callable stable ACP contract and distinguish native agents, maintained adapters, and unverified agent claims for the mobile feasibility decision.
Non-goal: install or authenticate agents, change gateway/UI code, or claim interoperability from documentation alone.

## Protocol and SDK findings

The [spec repository README](https://github.com/agentclientprotocol/agent-client-protocol#versioning) explicitly identifies **wire protocol 1 as current stable**. This research read actual `schema/v1/schema.json`, `schema/v1/meta.json`, and Rust model sources at commit [`9e032156545412be9bba5e092f12d0080c499b6d`](https://github.com/agentclientprotocol/agent-client-protocol/tree/9e032156545412be9bba5e092f12d0080c499b6d), dated 2026-10-01, schema artifact release 1.10.2. Schema/SDK package versions are separate from negotiated `protocolVersion`. The repository also publishes v2 and draft material; it is unsafe to infer stable v1 behavior from those pages.

* [Transport](https://agentclientprotocol.com/protocol/v1/transports): bidirectional JSON-RPC 2.0, UTF-8, one JSON envelope per newline over subprocess stdin/stdout; no embedded literal newlines and stdout is protocol-only. JSON strings can contain escaped newlines. Stderr may contain logs, so a relay must suppress/redact it. HTTP is a draft, not a stable interoperable ACP network endpoint. Custom transports must preserve message envelopes and lifecycle.
* [Initialization](https://agentclientprotocol.com/protocol/v1/initialization): client sends `protocolVersion`, `clientCapabilities`, optional `clientInfo`; agent returns its chosen version, `agentCapabilities`, `authMethods`, optional `agentInfo`. Refuse unsupported selected versions. Optional features must be negotiated rather than inferred from agent names.
* [Session setup](https://agentclientprotocol.com/protocol/v1/session-setup): `session/new` receives absolute host `cwd` and `mcpServers`; returns `sessionId` plus supported session configuration. `session/load` is gated by `loadSession: true` and replays retained conversation through `session/update` before its response. `session/resume` is distinct and capability-gated; it restores context without requiring history replay.
* [Session list](https://agentclientprotocol.com/protocol/v1/session-list) and [delete](https://agentclientprotocol.com/protocol/v1/session-delete) **are now stable optional v1 surfaces**, alongside resume/close. `agentCapabilities.sessionCapabilities.{list,delete,resume,close}` uses present `{}` for support, absent/null for unsupported. `session/list` takes optional `cwd` and `cursor`; returns sessions with mandatory `sessionId`/`cwd`, optional title/updatedAt, and optional `nextCursor`. This is not a promise that every agent lists durable historical sessions or retains every update.
* [Prompt turn](https://agentclientprotocol.com/protocol/v1/prompt-turn): `session/prompt` remains pending while agent sends `session/update`; final result carries `stopReason`. Baseline prompt text and resource links; image/audio/embedded-context support is negotiated. Updates include user/assistant/thought chunks, tool call/start/update, plan, commands, mode/config/session metadata, and usage. `session/cancel` is a notification; clients must still accept final prompt response and pending permission cancellation. A network reconnect has no general v1 cursor/sequence replay contract.
* [Tool calls](https://agentclientprotocol.com/protocol/v1/tool-calls): `tool_call` carries `toolCallId`, title, optional name/kind/status/content/locations/rawInput/rawOutput; `tool_call_update` patches the same ID. Status covers pending, in_progress, completed, failed. Kinds include read/edit/delete/move/search/execute/think/fetch/switch_mode/other. These are observations, not a generic client instruction to execute every agent tool.
* Tool-call content can hold standard content, a diff `{type: "diff", path, oldText?, newText}`, or an embedded terminal ID. A diff represents old/new text, not a standardized patch/revert operation. Preserve unknown variants privately for compatibility; never put arbitrary tool arguments into diagnostic logs.
* Permission is an **agent-to-client JSON-RPC request** `session/request_permission` with session/tool context and agent-supplied options. Option kinds include allow_once/allow_always/reject_once/reject_always; reply `{outcome: {outcome: "selected", optionId}}` or cancelled. Choose only an offered ID; never silently auto-allow when the phone is disconnected.
* [Filesystem](https://agentclientprotocol.com/protocol/v1/file-system) callbacks `fs/read_text_file`, `fs/write_text_file` operate on host absolute paths and are capability-gated. [Terminals](https://agentclientprotocol.com/protocol/v1/terminals) are client-provided `terminal/create`, `terminal/output`, `terminal/wait_for_exit`, `terminal/kill`, `terminal/release`; create includes command/args/env/cwd/output bound. Release terminates a running process and invalidates its ID. Mobile must route these to the trusted host and enforce workspace/process ownership, rather than interpret paths on Android.
* [Authentication](https://agentclientprotocol.com/protocol/v1/authentication): methods default to `type: agent`; `authenticate {methodId}` initiates agent-managed flow. Current stable v1 also supports `type: terminal` when client advertises `clientCapabilities.auth.terminal`: launch the configured agent interactively with advertised extra args/env, then reconnect/reinitialize; do **not** send its terminal-method ID to `authenticate`. Optional `logout` is gated by `agentCapabilities.auth.logout`. ACP does not standardize a universal API-key/OAuth credential exchange or remote-relay authentication. Keep provider credentials on the host; remote-device access needs its own authenticated Tailscale/SSH boundary.

The [official SDK list](https://github.com/agentclientprotocol/agent-client-protocol#integrations) includes Rust runtime/schema, TypeScript, Python, Kotlin and Java; no official Dart SDK is listed. TypeScript runtime [`src/acp.ts`](https://github.com/agentclientprotocol/typescript-sdk/blob/55dd3744bbd302768e79dc31d0ec77a46d82e60e/src/acp.ts) and Python [`src/acp/stdio.py`](https://github.com/agentclientprotocol/python-sdk/blob/9d07d7871ef4b220b8507e15fc4b1560f0950a64/src/acp/stdio.py) were read as implementation evidence. A small Dart stream client is plausible without native bindings.

The official Python SDK already ships [experimental HTTP/WS profiles](https://agentclientprotocol.github.io/python-sdk/web-transport/): HTTP/2 POST + connection/session SSE streams, or WebSocket JSON-RPC frames. Its documentation explicitly omits Last-Event-ID replay, sequencing and automatic reconnect/backoff. Treat this as implementation precedent, not a stable standardized relay contract.

Source/registry versions are observed evidence, not a guarantee that the installed PC version matches. ## Implications for the parent recommendation

ACP can plausibly reduce **conversation transport/event/approval adapters** for several additional agents. It does not unify installation, entitlement, sandbox guarantees, credentials, durable retention, worktree management, revert, or every vendor extension. Native integrations should remain when their semantics are richer. The separate [host research](acp-host-evidence-2026-10-02.md) found generic ACP support in our pinned Paseo v0.9.2, so the [consolidated recommendation](acp-research-2026-10-02.md) is staged adoption through that private host route before considering a separate BYO relay. Product enablement still requires agent/version pins, scoped history, phone-suspend permission cancellation and reconnect tests. Do not advertise many-agent compatibility on the strength of one fake-agent test.
