# Journey analytics: setup and chat (native), 2026-11-09

Scope: the native app only (Flutter is frozen). Baseline: GA4 property for 2.1.5, 32 users, 7 Nov to 9 Nov.
Privacy rules are unchanged and hold for every event below: opt-in only (`usage`), anonymous, no ad id, no Google
signals; only enums, kinds and coarse ranges; never prompt text, file names, paths, server URLs, keys, error text or
stack messages; the Firebase Performance network plugin is never applied; consent carries over from Flutter's keys
and is not touched here.

## 1. Why the params were blank

Read from GA (custom report, by hour) and from the 2.1.5 source (tag `v2.1.5+63`).

| Blank in GA | Cause | Fix in native |
|---|---|---|
| `setup_step_reached.step` blank, 48 events | GA only fills a custom dimension from the moment it is registered. All 48 are from 8 Nov 20:00 to 21:59 (hour 21 also has filled rows); from 22:00 on every row has a step. Not a code bug. Same for the 11 blank `send_result.first_reply_range`, the 60 blank `jank.screen`. | none needed; nothing is lost going forward |
| `setup_step_failed.fail_kind` always blank | Flutter sent the param as `kind`, not `fail_kind`. `kind` is registered, so the 15 events do show `kind = other`, but the dashboard column people read (`fail_kind`) never gets a value. Also every one of them says `other`: the classifier only looked at error text, which the setup engine does not put in the field. | the event is folded into `linux_setup_step` (result `fail`) and the kind comes from the typed setup error, so it is `network`, `storage`, `apt` (package install failed), `permission`, `download`, `checksum`, `killed_by_system`, `timeout` or `unknown`, sent as `fail_kind` |
| `setup_done.server_kind` always blank | Never sent. The event carried one param, `minutes`, and `minutes` is not a registered dimension (`minutes_range` is), so the total time was invisible too. | `setup_done` sends `minutes_range` and `server_kind` |
| `first_reply.first_reply_range` blank | `first_reply` was written with `seconds` (not registered) and `server_kind`. `first_reply_range` belongs to `send_result`, where it is filled (77 `2-10s`, 15 `10-30s`, 14 `<2s`, 4 `none`). | `first_reply` sends `first_reply_range` and `server_kind` |
| `session_length` has no value | Same family: it carried `minutes`, not `minutes_range`. 358 events, nothing readable. | sends `minutes_range` |

Nothing was dropped for length (all values are under 40 characters) or for type (every value is already text).

Rule used from now on: a param name is the name of a registered dimension, and a unit test fails if a journey event
uses a name that is neither registered nor in the "to register" list below.

## 2. Setup journey

First run until the phone's own server works. Steps are the setup engine's components: `linux`, `essentials`, `python`,
`node`, `opencode`, `start`, `voice` (optional), plus `aiteam`.

| Event | When | Params |
|---|---|---|
| `setup_step_reached` | a step starts | `step` (`linux`, `essentials`, `python`, `node`, `opencode`, `aiteam`, `voice`, `start`, `other`), `attempt` (`1`, `2`, `3+`) |
| `linux_setup_step` | a step ends (the name is kept so Flutter history stays one series) | `step` (`unpack`, `essentials`, `node`, `opencode`, `paseo`, `agents`, `start`, `voice`, `done`), `result` (`ok`, `fail`, `skipped`, `cancelled`), `attempt`, `ms_range` (duration), `fail_kind` (on fail only), `free_space_range`, `compat_mode`; `exit_kind` and `signal` only when an exit code exists (native steps have none, so they are left out instead of sent as "unknown") |
| `setup_done` | the first-run job finishes | `minutes_range` (whole setup, first start to done, wall clock: `under_2`, `2_to_5`, `5_to_10`, `10_to_20`, `20_to_40`, `over_40`), `server_kind` (`phone`) |
| `setup_abandoned` | setup is unfinished and the person has been away 5 minutes or more: app backgrounded while the job is not running, or app closed (reported at the next start) | `step` (last step reached), `reason` (`background`, `closed`), `minutes_range` (time away: `5-15`, `15-60`, `60-1440`, `>1440`) |
| `setup_resumed` | the person comes back and the job runs a step again | `step`, `minutes_range` (time away) |

Definitions that matter when reading the numbers:
- `attempt` counts the starts of that step since the last finished setup, kept across restarts (a small preference,
  words and numbers only). Attempt 2 means a retry or a resume.
- A step that was already installed is `skipped` (duration 0), not `ok`.
- A job cancelled by the person ends the running step as `cancelled`; a job the system interrupted ends it as `fail`
  with `fail_kind = killed_by_system`.
- A running setup that carries on in the background is not abandoned. Abandoned means "stopped and left".
- `setup_done`, `setup_abandoned` and `setup_resumed` are for the first-run job only; step events are for every job
  (adding a tool later is also a step).
- Not covered: leaving before tapping Start. That shows as `screen_view` `setup` with no `setup_step_reached` after it.

Questions answered:
- Where do people drop in setup? `setup_abandoned` by `step`; and steps with `setup_step_reached` but no
  `linux_setup_step` (the process died or the person left mid-step).
- Which step fails, and why? `linux_setup_step` result `fail` by `step` and `fail_kind`.
- Does retrying work? Success rate of `attempt = 2` against `attempt = 1`.
- How long does setup really take? `setup_done.minutes_range`, and `ms_range` per step to find the slow one.
- Do people come back? `setup_resumed` count over `setup_abandoned` count, split by time away.
- Is storage the problem? `fail_kind = storage` against `free_space_range`.

Funnel: `setup_step_reached(linux)` then `...(essentials)`, `(node)`, `(opencode)`, `(start)`, then `setup_done`.

## 3. Chat journey

Send a prompt until the reply is done. Fed by the prompt timeline (ids only), the stream status, Stop, and the
approval list.

| Event | When | Params |
|---|---|---|
| `send_result` | the first reply arrives (`ok`), the turn ends with none (`ok`, `first_reply_range = none`), the send is refused (`fail`) or held offline (`queued`) | `result`, `fail_kind` (on fail: the connection kinds plus `rejected`, `too_large`, and for a turn the model refused with no reply `rate_limit`, `free_limit`, `sign_in`, `model_error`), `first_reply_range` (time to first token: `<2s`, `2-10s`, `10-30s`, `>30s`, `none`), `agent` (`build`, `plan`, `general`, `other`: a custom agent name is never sent), `server_kind` (`phone`, `computer`), `input` (`text`, `voice`, `attachment`, `voice_attachment`) |
| `chat_turn` | the turn ends, or the stream never came back | `outcome` (`done`, `stopped_by_user`, `error`, `connection_lost`, `approval_timeout`), `ms_range` (send to done: `<10s`, `10-30s`, `30-120s`, `2-10m`, `>10m`), `first_reply_range`, `tools_range` (`0`, `1-3`, `4-10`, `11-30`, `>30`), `fail_kind` (error turns: `provider_auth`, `rate_limit`, `free_limit`, `context_overflow`, `output_length`, `content_filter`, `model_not_found`, `aborted`, `server`, `other`), `recovered` (`none`, `yes`, `no`: did the stream drop during the turn, and come back), `follow_up` (`none`, `steer`, `after_fail`), `agent`, `server_kind` |
| `turn_stall` | a running turn has been quiet for 1, 5, 15 or 60 minutes (once per range) | `stage` (`waiting_tool`, `waiting_approval`, `streaming`, `other`), `minutes_range` |
| `approval` | an approval or question closes | `kind` (`run`, `edit`, `read`, `web`, `question`, `other`), `result` (`allowed`, `always`, `denied`, `answered`, `declined`, `expired`), `ms_range` (asked to answered) |
| `first_reply` | the first reply this install ever saw, once | `server_kind`, `first_reply_range` |
| `feature_used` | voice dictation handed back words, a file was attached | `feature` (`voice`, `file_attach`) |
| `conn_attempt`, `conn_drop` | unchanged from 2.1.5 | as before |

Definitions:
- A reconnect during a turn is not its own event: it is `recovered` on that turn's `chat_turn`. A stream that has not
  come back two minutes after dropping ends the turn as `connection_lost`, `recovered = no`.
- `steer` is a prompt sent into a running turn (no second `chat_turn`). `after_fail` is the next prompt within two
  minutes after a turn that ended in error or lost its connection. This is a proxy for "retry"; the app cannot tell a
  retyped prompt from a tapped Send again without reading the text, which it must not.
- `approval_timeout` is a turn that ended in error after an approval left without an answer.
- `expired` is an approval that left the list without the person answering.
- Time to done is measured on the phone's clock from the send to the idle/error signal; it includes the wait for approvals.
- Not covered: a turn the process never finishes (app killed). It has `send_result` and no `chat_turn`; the gap is
  itself the signal.

Questions answered:
- How often does a reply never arrive? `send_result` with `first_reply_range = none`, and `chat_turn` outcomes
  `connection_lost` and `error`.
- How long do people wait? `first_reply_range` and `chat_turn.ms_range`, by `server_kind` and `agent`.
- Is the phone's server slower than a computer? Same, split by `server_kind`.
- Why do turns fail? `chat_turn.fail_kind` for `outcome = error`.
- Do approvals block people? `approval.ms_range` and `expired` share; `turn_stall` with `waiting_approval`.
- Do reconnects save the turn? `recovered = yes` against `no` over turns with a drop.
- Do people stop turns or steer them? `stopped_by_user` share; `follow_up = steer`.
- Do voice and attachments change the outcome? `send_result.input` against `chat_turn.outcome` (by `agent`/`server_kind`).
- How big are turns? `tools_range`.

## 4. GA registration (owner action)

The service account is read-only, so these need the GA console (Admin, Custom definitions, Create custom dimension).
All are event scoped; the event parameter name equals the dimension name.

Register these five (new):

| Dimension name | Scope | Event parameter | Used by |
|---|---|---|---|
| Attempt | Event | `attempt` | `setup_step_reached`, `linux_setup_step` |
| Outcome | Event | `outcome` | `chat_turn` |
| Input | Event | `input` | `send_result` |
| Tools range | Event | `tools_range` | `chat_turn` |
| Follow up | Event | `follow_up` | `chat_turn` |

Everything else reuses the 25 dimensions already registered (`agent`, `fail_kind`, `first_reply_range`, `kind`,
`minutes_range`, `ms_range`, `recovered`, `reason`, `result`, `server_kind`, `stage`, `step`, `free_space_range`,
`compat_mode`, `exit_kind`, `signal`, `feature`, `screen`, `janky_pct_range`, `refresh_hz`, ...). After this the
property uses 30 of 50 event-scoped dimensions. Some dimensions are shared by several events with different word lists
(`ms_range` is a connect time on `conn_attempt`, a step time on `linux_setup_step`, a turn time on `chat_turn`);
always filter by event name when reading them.

Data appears in a dimension only from the moment it is registered, so register before the native build is released,
or the first days will look blank like the 48 above.

## 4b. Setup to first reply: where the people are lost

Baseline from the product research: of 35 people, 24 started phone setup, 18 finished, 13 ever got a reply.
Read it as one funnel in a GA funnel exploration (open funnel, per user, step 1 to 7 in order). Every drop has an
event that says why:

| Step | Event (filter) | If people are lost here, the cause is in |
|---|---|---|
| 1 Started phone setup | `setup_step_reached` `step = linux` | n/a (before this: `screen_view` `setup` without it) |
| 2 Passed each tool | `linux_setup_step` `result = ok` per `step` | `result = fail` by `step` and `fail_kind`; `setup_abandoned` by `step` and `reason`; `step reached` with no end |
| 3 Setup finished | `setup_done` | the same, plus `setup_resumed` (came back) vs `setup_abandoned` (did not) |
| 4 Phone server answers | `conn_attempt` `server_kind = phone` | `result = fail` with `fail_kind` (the server did not start or refused) |
| 5 Opened a chat | `screen_view` `screen = chat` (now always carries `screen`) | no chat screen after step 4: the ready screen or project step loses them |
| 6 Sent a prompt | `send_result` (any `result`) | `result = fail` with `fail_kind`, or `queued` (offline) |
| 7 Got a reply | `first_reply` (once per install) | `send_result` with `first_reply_range = none`; `chat_turn` outcome `error` (with `fail_kind`), `connection_lost`, `approval_timeout`; `turn_stall` |

So the 24 to 18 loss is read from steps 2 to 3 (`fail_kind`, `setup_abandoned.step`); the 18 to 13 loss from steps 4 to
7: someone who finished setup and has no `conn_attempt ok` is a server that never came up; with it but no chat
screen is a navigation loss; with a chat screen but no `send_result` never typed a prompt; with `send_result` but no
`first_reply` is read from the none/error/connection_lost rows. This is why `first_reply` is a separate once-per-install
event: it is the funnel's last step.

### Is `jank` useful?

Yes, and the native numbers are comparable with Flutter's.
- Flutter 2.1.5: for each frame, `totalSpan > 1 / refresh rate`; per screen kind; sent once per session per screen
  when at least 30 frames; `janky_pct_range` (`<1`, `1-5`, `5-15`, `>15`), `refresh_hz` (`60`, `90`, `120`, `other`).
- Native: the window's frame metrics, `TOTAL_DURATION > 1 / refresh rate` per frame, the same per-screen session, the
  same 30-frame minimum and the same ranges and hz words (`JankMeter` is a port of Flutter's).
So the two series can be put on one chart. Caveats: the Android total includes the input and layout phases the
Flutter span starts after, so native will read slightly worse on the same phone; compare at equal `refresh_hz`. The
60 blank `screen` values in the baseline are the registration gap described in section 1.
Kept as is.

### For the owner (debatable, not built)

1. Drop `app_open`? It makes `app_start` the only launch event. Cost: the Flutter `app_open` series ends.
2. `setting_changed`: it is the only way to learn which style and theme people pick, but it adds two params
   (`setting`, `value`) and a hook in each settings presenter. Values would be closed lists, never free text.
3. `app_exit` event: gives crash and ANR kinds in GA without opening Crashlytics. Same privacy class as the existing key.
4. `agents_used` / server mix as user properties (counts only, no names).
5. Whether `first_reply` and the first `send_result` should be one event. They are kept apart because `first_reply`
   is once per install (the activation metric) while `send_result` is per prompt.

## 7. Findings folded in from the first-reply investigation

- Setup failures were always `other`: the classifier read error text the setup engine never supplied, and Flutter's
  `linux_setup_step` lost the exit code. Native classifies from the typed setup error (the error class), so the kind is
  a closed word; the exit code is sent (`exit_kind`, `signal`) whenever one exists and left out when it does not. The
  native setup progress carries no exit code, so today these two are absent; a builder that adds an exit code to the
  step result gets it in `linux_setup_step` with no schema change. Word mapping to the coordinator's list: space is
  `storage`, killed is `killed_by_system`, apt is `apt`, the rest are the same.
- Param names now match the registered dimensions (`minutes_range`, `first_reply_range`, `fail_kind`).
- Model errors no longer count as `ok`: a turn that ends in a model error with no reply is `send_result` `fail`
  (`rate_limit`, `free_limit`, `sign_in`, `model_error`), and the turn is `chat_turn` `error` with the same cause. The
  rate-limit and free-tier words are read from the server's symbolic error tag, never its text. `turn_stall` is called
  by the journey tick for any turn quiet 1, 5, 15 or 60 minutes.
- Phase 0 kinds (native/next 6ba3a2f2b): `SetupError.StepTimedOut` (`step_timeout`) is `fail_kind = timeout`. A failed
  turn's own words are classified by the existing `AgentRunFailureKind` (sign-in, no credit, busy, model unavailable,
  connection lost) and only the closed word goes on: `provider_auth`, `free_limit`, `rate_limit`, `model_not_found`,
  `provider_connection`; the words are never stored or sent. `StartProblem.TimedOut` (waiting for the phone's server) is
  a screen state, not an event; the same wait shows as `conn_attempt` `fail_kind = timeout`.
