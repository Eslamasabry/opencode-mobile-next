## Real installed Paseo and isolated file replacement

[emulator.log](emulator.log) records the production `PaseoPhoneScripts.check`
generated by pinned Dart from both baseline and fixed source, without modifying
the scripts. It runs them in the installed app's Ubuntu/PRoot with agent uid
1000 and an empty scratch HOME. Only temporary fake files are bound over the
installed code paths for each child PRoot; the underlying installed files stay
intact.

The real 0.9.2 CLI passes the pinned wrapper, entry payload, entire `bin`/`dist`
code tree, version and `daemon run --help` checks. The genuine help exposes
`--home <path>`; it has no `--foreground` flag. No daemon is launched by this
probe. Only the bounded expected version projection is accepted, and no raw
CLI stdout/stderr is written to the evidence log.

Three replacements are tested separately: `bin/paseo`, `dist/index.js`, and
`dist/run.js`. Each counterfeit reports the expected 0.9.2 version and writes
an execution marker in scratch if run. In all three cases:

- Baseline returns 0 and executes the counterfeit.
- Fixed returns 1 before the counterfeit executes; the marker stays absent.
- Genuine installed Paseo passes again after all temporary bindings end.

Pins observed on the emulator match the verified package artifact:

- Wrapper SHA-256: `2b761f40e5a6416e4aaa733f38a47d5a4639b42cc1f88fc060256d2c4ed8cf94`.

The deeper `run.js` replacement matters: the executable wrapper is a 76-byte
import, and its entry payload imports further implementation code. Pinning only
those two loader files would leave the actual program replaceable.

## Production native host on Android

[native-emulator.log](native-emulator.log) records the exact source hashes for
`PhoneAgentHost.kt` and its extracted production `SetupDiskSpace` object. The
real native host is compiled with the root lead's controlled Linux transport
stub and `phone_agent_host_harness.kt`, converted through D8, and executed with
Android `app_process`. Android's actual `Build` class and actual child-process
runtime are used. Standalone `dalvikvm` could not initialize framework
`SystemProperties` native methods; `app_process` registers those methods.

- Immediate exit: a controlled child reads the synthetic password, waits 0.2
  seconds, emits an injected private-output marker and exits 7. The real host
  rejects it before tracking it as running, reports "stopped as soon as it
  started" with setup-check/retry guidance, and never includes the injected
  output in its error or log.
- Healthy launch: the real host accepts a surviving child, tracks it as
  running, and stops it through its exact process handle.
- Low space: the real host rejects admission before any config write, launch
  or service tracking (`configWrites`, `launches`, and `tracked` are all zero).
- Concurrent start: the first launch is held at a controlled barrier before
  registration. Another profile is rejected while that launch is pending,
  before it writes configuration or starts a process. The first launch then
  completes; exactly one config write and one process launch occurred.

The native artifact was refreshed after the startup reservation fix and includes
all four scenarios against the final source hash. This checks the native host's
startup window, output handling, concurrent admission and disk admission on
Android. The controlled Linux transport does not exercise the APK channel,
actual PRoot daemon launch, profile persistence, Keystore or network. The shell
probe exercises the installed checker, rather than downloading/installing a
candidate; named installation checksum/version/launch stages have separate
candidate-script regression evidence recorded by the BC lead.
