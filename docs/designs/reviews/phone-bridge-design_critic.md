# Phone bridge: Design Critic goldfish review

Target: `docs/designs/phone-bridge-2026-11-09.md` (v1 draft, 498 lines). Mode: REVIEW. Reviewer: egm-design (Design Critic). Weighted hardest on security and the Android API claims, as asked. Read-only; evidence from the doc and these code paths: `native/core/security/.../Links.kt`, `native/android/schedules/.../ScheduleExactAlarms.kt` and its manifest, `native/android/linux/src/main/AndroidManifest.xml`, `native/androidApp/src/main/AndroidManifest.xml`, `native/android/linux/.../NativeServerRecipe.kt`, `engine/linuxtools/.../SharedStorageBindSourceTest.kt`, root `AGENTS.md`.

Verdict: not ready to build. Two Blockers in the trust model (the loopback transport and the "site grant" data-leak bound), several Majors. The confirm-as-safety-line idea is sound; the pieces around it have holes.

## Blockers

### B1. Loopback TCP lets another app squat the port and harvest the bearer secret (and feed the agent hostile tool text) - section 2.2, T4 in 3.1
The doc defends against other apps *calling* the bridge (secret, Origin, Host). It does not defend against another app *being* the bridge. The port is "stable per install, chosen once, re-chosen only if taken" (section 4, "Bridge restart"). Any app with INTERNET can bind a free 127.0.0.1 port. If the bridge is down (app killed, reboot, before the service starts) a squatter binds the stored port, the agent connects, and sends `Authorization: Bearer <secret>` in clear to the squatter. The squatter now has the secret and, worse, answers `tools/list` and `tools/call` itself: tool descriptions and results are an injection channel straight into the agent's context, and the phone never sees the call, so no confirm and no log exist. "Re-chosen if taken" only fixes the bridge, not the secrets already sent. The MCP client cannot authenticate the server.
The UDS rejection in 2.2 ("every guest process has our user ID anyway") answers the wrong threat: a UDS inside app-private storage excludes other apps, which TCP cannot, and that is exactly T4. The doc even admits other apps can find the port.
Recommendation: make the transport something other apps cannot occupy or reach. Options: (a) Unix socket in the app's private dir, bind-mounted into the guest (BuiltinLinux already uses `--bind=`), with a small stdio/HTTP shim per agent config; (b) keep TCP but have the bridge hold the port from app start (service-owned, bound before any agent starts, `SO_REUSEADDR` off) and add a per-start proof, e.g. the agent entry carries a header the squatter cannot answer, though this is still unauthenticated for the client; (c) accept TCP only after a spike proves the squat window is closed. Do not call this settled until one of these is decided, and add a squat test to 4.1 (second APK binds first).

### B2. The "this site for this conversation" grant and the 64-character query threshold do not bound data exfiltration - T2 (3.1), grant table (3.2), 5.2
Open-URL is acknowledged as an outbound data channel, yet the proposed bound is a guessed 64-character query length (T2, "guess threshold"). 64 characters carries an API key, an SSH key fingerprint, a JWT prefix, a password, or a one-time code. Path segments and the fragment are not mentioned at all (`https://github.com/<64+ chars of secret>` or `.../<secret>.png`), and a path to a host the person already allowed is still a request that lands in that host's logs. A pre-approved host that offers user-controlled content (a GitHub new-issue URL with a prefilled body, a paste service, any URL-shortener host, a `*.github.io` / `*.vercel.app` / `*.pages.dev` site) turns "Allow github.com for this conversation" into a free exfil route and, because the grant is session-long, an injected agent can use it repeatedly without a second confirm. An open redirect on an allowed host defeats the host check as well (Custom Tabs follow redirects).
Also `ExternalLinkPolicy.check` (Links.kt) returns `AskFirst` with only `shownHost`; it does not compute punycode, does not look at query/fragment, and allows plain `http` (flagged `insecure`). The doc's T5 punycode display and T2 query flags are therefore new code, not reuse.
Recommendation: site grants cover only URLs with no query and no fragment and a path under a fixed length, per exact origin (scheme+host+port); any URL with a query, fragment, or high-entropy path segment asks every time; no site grants for shared-hosting suffixes (use the public-suffix list); never grant for `http`. Show the whole URL, not only the host, and mark the part after `?`/`#`. Cap the cumulative granted URLs per conversation (rate limit exists: 5 per 10 min, which still leaks 5 secrets in 10 min; lower to a total per conversation).

## Major

### M1. The confirm shows facts the bridge cannot verify - 3.2 "Confirms", 5.2
"Asked by Claude Code - 'Fix login retry' - This phone" and "The agent says: ..." appear in a trusted sheet. The agent identity is the token owner, and the token is per (profile, agent), so any guest process holding it (the doc's own T3) is labelled "Claude Code". The conversation title comes from the correlation (2.2), which can fail or be mis-matched; the "reason" is attacker-controlled text rendered in the safety UI. A confirm that looks authoritative but is partly attacker-chosen is a social-engineering aid. Recommendation: show only what the bridge itself knows (ability, exact normalised arguments, which agent token, "conversation not identified" when correlation fails). Render the agent-supplied reason in a visually distinct, collapsed or clearly quoted way, with length cap and sanitising, or drop it for Act/Out in v1. State in the sheet when the conversation is unknown.

### M2. Conversation correlation is spoofable and racy, and the grants hang on it - 2.2 "Which conversation is calling?", 3.2
Match key: same tool and argument hash within about 2 s. A guest process can fire the same hash and steal or consume the match, so the legitimate call falls to "ask" (a DoS on grants), or a stolen match could inherit a conversation grant for a call whose arguments the attacker chose only if they equal the agent's. Parallel sub-agents or a retry also break "single match". The doc's fallback ("unknown means ask") is safe, but then "Allow for this conversation" works only when the stream is watched, which is an unmeasured assumption; the spike (open question 1) decides whether the whole grant level exists. Mark per-conversation grants as conditional on that spike; until then ship only "Allow once". Also say what happens when the event stream is delayed more than 2 s (the tool part may arrive after the HTTP call).

### M3. Idempotency by derived key swallows legitimate repeats and claims success - section 4 "Idempotency", 3.4 "Duplicate"
"The bridge also derives a key: hash(profile, conversation-or-agent, ability, normalised arguments). A repeat within 24 hours returns the stored result and does nothing." So "notify me: build finished" twice in a day, "open the PR" a second time after the person closed the tab, or "copy this command" again after the clipboard changed returns success and does nothing. The agent reports success the person never sees. Reminder uniqueness is fine (a reminder has a time and a text), but notify/open/copy/share must not be deduped by content. Recommendation: only dedupe on an agent-supplied `request_id` (and a short window for the derived key, 60 s, or none). Also state where results are stored: in memory they vanish on app kill, which is exactly the retry-after-kill case the doc claims to cover; reminders have a DB constraint, the others do not.

### M4. Kill between "approved and executed" and "result and log written" - 3.3 "App killed", section 4
Doc: "no call is left half-done" and "pending confirms are lost on purpose". The unsafe window is after Allow: the action runs (reminder row written, tab opened, notification posted), the process dies before the result is returned or the log entry is written. The agent (or an orphaned agent process, see M5) retries, and for non-reminder abilities the idempotency store is not durable, so it re-asks (fine) or, with a conversation grant, re-executes silently (a duplicate). The log may be missing an executed action, which breaks "every call is in a log". Recommendation: write an intent record (state `approved`) before the Android call and `done` after, in the same durable store as reminders; on start, reconcile: log "interrupted" for anything left in `approved`; grants-based re-execution of an interrupted call asks again.

### M5. "The guest and agents die with the app, so nothing is left half-done" is probably false - 3.3, 7 (last rows)
Project memory records orphaned proot agent shells (`ppid 1`) surviving after proot death, and the doc's own model has proot children of the app. If the app process dies, orphaned agents may continue and retry against the restarted bridge on the same stable port and secret. Treat agents as able to outlive the bridge. Also the revoke path (rotate secrets) must handle a running agent holding the old secret: it gets 401s, so define what the transcript and Settings show.

### M6. The Out-class confirms are moot while the guest can read shared storage directly - section 1 catalogue rows 9, 13; "What exists today"
Row 13 admits "This phone agents can already see shared folders on disk". `SharedStorageBindSourceTest` shows `--bind=/storage` and `/sdcard` outside the confined (AI Team) tier, with a broad-access choice. DCIM, Downloads and screenshots are then readable by any agent or guest process with no bridge call. The promise "Nothing leaves the phone without a confirm" (3.2) is false for those paths, and the doc does not say so. Either scope the claim ("through the bridge") and state that shared-storage access is governed elsewhere, or tie the bridge's Out-class story to the confined tier. Also note photos picked through the picker carry EXIF (GPS); strip location metadata before returning (not mentioned).

### M7. Failed-secret lock-out is a DoS lever for any app - 2.2, T4
"Pauses after 5 wrong secrets a minute": if the pause is global, any app on the phone can lock out the real agents indefinitely with six wrong attempts per minute. A 256-bit secret cannot be brute-forced, so the lock-out buys nothing. Remove it or make it per-connection with a short penalty; use constant-time comparison; log the count, not the callers.

### M8. Exact-alarm and reminder claims are partly wrong or unsupported for Android 14+ - catalogue row 1, 3.4, 3.3, 7
- Row 1 says Android 14+ requires the person to grant it. Correct, with precision: for apps targeting 13+ installed fresh on Android 14+ `SCHEDULE_EXACT_ALARM` is denied by default; when the person revokes it, the system kills the app and cancels all its exact alarms. The existing `ScheduleExactAlarms` handles `SecurityException` and checks `canScheduleExactAlarms`. The doc's re-arm list includes `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED`, which only fires on grant, so the "revoked mid-flow" case is handled by the app being killed, not by a broadcast. State it.
- `setAlarmClock` is mentioned in row 1 but not chosen. It needs no `SCHEDULE_EXACT_ALARM`, is exempt from Doze throttling, shows the alarm icon, and is the right primitive for "a reminder that rings". It removes the permission step, the Play exact-alarm justification (section 7, risk row "Play review") and the fallback. The doc should decide on it or explain why not (the alarm-clock chrome in the status bar is the trade-off).
- 3.4 promises "may ring up to 10 minutes late" for the WorkManager fallback. WorkManager gives no such bound; deferred work in Doze can slip by far more (maintenance windows, standby buckets). Remove the number or say "may be late".
- `setExactAndAllowWhileIdle` is throttled while idle (about one per 9 minutes per app) and is not the same as ringing; "ring" needs a notification channel with alarm audio attributes, or a full-screen intent. `USE_FULL_SCREEN_INTENT` is Play-restricted from Android 14 for non-alarm/calling apps. The doc says "a reminder that rings" in the finish line and never specifies the sound, channel importance or lock-screen behaviour.
- The Play risk row asserts "Reminders are a user-visible alarm feature (allowed reason)". Play's exact-alarm policy admits calendar/alarm/timer core functionality; an agent-reminder feature in a coding-agent client is arguable. The app already declares the permission for scheduled runs, so the real work is aligning one declaration with two uses. Flag as unverified.

### M9. The background confirm depends on POST_NOTIFICATIONS, which the person may deny - 3.3, 5.1
The confirm for a backgrounded app is a notification. If notification permission is denied or the channel is muted, no confirm is visible, calls time out at 5 minutes and the agent holds a connection. 5.1 asks for the permission "when the ability is turned on", but the confirm channel is needed by every ability. Specify: if notifications are blocked, calls from the background fail at once with a plain message, and the Settings page shows the missing permission. Also specify the channel importance (heads-up) and that Android 13+ lets the person dismiss the permission prompt twice, after which only Settings works.

### M10. Revoke rotates secrets, but agent sessions read config at start - 3.2 "One-tap revoke", 2.2 registration table
Claude Code and Codex read MCP config at session start; rotating the token and rewriting files breaks running sessions (401) and the doc does not say how re-enabling brings them back (restart the agent session?). It also does not say where the "file reference" secret lives for OpenCode (`{file:...}` inside the guest, readable by every guest process and by the agent through its own shell, so the model provider sees it if the agent `cat`s it). That is consistent with "the secret is not the safety line", but then the doc should stop calling it a secret in the user-facing story and in 3.1 T3/T4 accounting. Define the re-enable flow.

### M11. Rushing the confirm - T5 (3.1), 5.2
500 ms delay on the primary button is short and applies only to the sheet. Notification actions (Allow / Don't allow on the heads-up notification, 3.3 for Local class) have no delay and a rushed thumb hits them. A sheet that appears under the person's finger while typing in the composer causes mis-taps; the doc relies on `filterTouchesWhenObscured`, which only drops touches on obscured views, and a Compose `ModalBottomSheet` is its own window, so the filter must be set on that window's decor view. Recommendations: ignore touches that began before the sheet was drawn, use 1 s or more for Act/Out, remove Allow from heads-up notification actions for anything but Fact-adjacent Local (the doc already limits to Local; make "Allow" on a notification single-ability, no "for this conversation"), and keep `setAuthenticationRequired(true)` on every notification action.

### M12. Plain `http`, redirects, App Links and GET side effects in Custom Tabs - catalogue row 5, 5.2
`ExternalLinkPolicy` allows `http`; for an agent-originated open the bridge should refuse `http` (or confirm with a loud insecure marker). Custom Tabs carry the person's cookies: a GET to a logged-in site that has state-changing GET endpoints acts as the person (CSRF-by-link). Some https links resolve to another installed app via App Links (messaging, payments), so "opens in the phone browser" is not guaranteed. Mention these in T1/T2 and state the policy: no `http`, no state-changing-looking paths is unenforceable, so tell the person the consequence in the confirm copy ("opens with your browser logins").

## Minor / nits

- N1. MCP versions: the doc says the 2026-07-28 spec drops `initialize` and session ids and that the server serves both eras. Serving both on one endpoint is a real implementation risk (detection logic, duplicate test matrix). Pick the oldest still used by the four agents plus the newest; confirm by spike before claiming "costs little" (2.2).
- N2. Row 17b and several "Guess" rows are fine as guesses; row 6c ("Guess: Chrome accepts only shell/root peers") is a v3 detail with no effect on v1. Fine to leave, but it distracts from the Blockers.
- N3. T6 says Out/Act confirms need the phone unlocked; the sheet inside the app obviously does, but a sheet over the lock screen via full-screen intent would bypass it. State that no full-screen intent is used.
- N4. Rate-limit tables are all labelled "first guesses". Acceptable at v1 draft, but "Reminder: 50 pending" with a 20/day creation cap means one injected conversation can fill the person's reminder list; give a per-conversation cap too.
- N5. Foreground service claims check out against manifests: `BuiltinServerService` is `specialUse` (no timeout) and `BackgroundConnectionService` is `dataSync|shortService`. Correct as written. Note the Play Console `specialUse` declaration text in the manifest says "on this device only"; hosting a loopback tool server for agents fits, but reread the text when the bridge is added.
- N6. Target SDK is 36 in the build logic (`Sdk.TARGET = 36`); the doc speaks of Android 17 in open question 7 only. Fine.
- N7. D6 recommends setting the agents' own permission to "allow" for `phone_*`. Combined with M1/M2 (confirm labels are weakly verified), say plainly that if the phone sheet is bypassed or mis-labelled, no second layer remains; keep the agents' default prompt for Act/Out-class tools (option B) unless the phone sheet is shown to be airtight.

## What holds up

- Treating the caller as hostile and putting safety in the on-phone confirm (2.2 last bullet) is the correct frame.
- Off by default, no queue for remote, no "Always" on risky abilities, redacted log (T8) and per-profile storage key naming match AGENTS.md invariants.
- Reuse of `ExternalLinkPolicy` for the open-URL path honours the "never launchUrl a server value" invariant.
