# Phone bridge: Implementation Readiness goldfish review

Target: `docs/designs/phone-bridge-2026-11-09.md` (v1 draft, 498 lines). Mode: REVIEW. Reviewer: egm-implementation-readiness (Tech Lead / implementer). Question for each part: could I start coding it tomorrow without making a design decision? Code checked: `native/` module tree, `Oc2Operations.mcpAdd`, `ScheduleExactAlarms`, manifests, `Links.kt`, `engine/requests`.

Verdict: not ready. The policy narrative is detailed, but the interfaces an implementer needs (tool schemas, data model, error codes, module contracts, lifecycle owner, state machine) are absent, and several mechanisms rest on spikes that have not run. Estimated "about 3 weeks" is not supportable until those are written.

## Blocker

### R1. No tool contract: names, argument schemas, result shapes and error codes are not defined - 2.1, catalogue 1.1, 3.4
The tools are named only in passing (`phone_remind`, `phone_open_url`, `phone_reminders_list`, `phone_reminder_cancel`, `phone_abilities`; the rest implied). There is no table of: tool name; input JSON schema (fields, types, limits: text length, max time horizon, URL length, photo size/dimensions, file size and allowed MIME for save); output shape; MCP annotations (`readOnlyHint`, `destructiveHint`, `openWorldHint`) per tool; and the stable error codes behind the plain sentences in 3.4. The implementer has to invent the public API that four agents will be configured against. Provide: one table of tools with JSON schemas, one table of error codes (code, plain sentence, retryable?), and a rule for how the agent gets a refusal (MCP `isError` content, not a JSON-RPC error).

### R2. Who owns the HTTP server, and what is its lifecycle? - 2.1, 2.2, 3.3, "Nothing in the bridge starts its own foreground service"
The doc places the bridge "in the app process" and "inside whatever keeps the app alive", while the keeper is `BuiltinServerService` (`android/linux`, `specialUse`). Undefined: which module starts the listener; whether it starts with the service, with the app, or on first agent registration; what happens when the service stops but the app lives (agents in the guest are gone, fine) and when the app is alive without the service (remote servers, v2); how the stable port is stored (where, with what key, after reinstall/backup restore); what binds first on boot (the guest server needs the entry written before it starts); and how the bridge gets the confirm UI when no Activity exists. Provide a lifecycle diagram or table: start trigger, owner class, stop trigger, restart, port persistence. `android/phonebridge` and `engine/phonebridge` do not exist in the module tree or `MODULE_OWNERS`, so the module contract (public API of the engine, what the android module implements, Metro/DI wiring) is also missing.

### R3. The core policy is a state machine that is described in prose only - 2.1 steps 1-8, 3.2, 3.3
Steps 1 to 8 are a pipeline, but the states are not: `Received -> Validated -> PendingConfirm -> Approved -> Executing -> Done/Failed/Interrupted`, with transitions on timeout, revoke, grant revoked while pending, app kill, duplicate request, and second request while two confirms are pending ("waits or fails": which?). The implementer must decide: is "wait" a queue with an order, is the 5-minute timer started at arrival or at display, does a grant expiry cancel an in-flight call, what are the idempotency semantics when the first call is still pending. Provide the state table and the persistence for each state (what survives a kill; section 3.3 says pending confirms are lost, but the log and the intent record are not specified). Add the invariants the tests assert (e.g. "no Android adapter call without an `Approved` record whose argument hash equals the call's").

### R4. Conversation identification is an unresolved spike that the grant model depends on - 2.2, 3.2, open question 1
"Plan: correlate" via tool part plus argument hash within about 2 s. The implementer needs: which event stream and which event type carries the tool part for OpenCode 2, OpenCode 1, Claude Code via Paseo, and Codex; whether the stream delivers before the HTTP call; the exact hash input and normalisation; the tie-break; the cache size and TTL; how it is tested without the real agents. Until the spike runs, the grant levels "this conversation" and "this site for this conversation" cannot be implemented. Gate the grant feature on the spike and write the v1 fallback precisely ("Allow once" only).

## Major

### R5. Data model and storage are not specified - 3.2 "Activity log", 4 "Reminders", 2.2 secrets
Missing: tables or records for reminders, grants (scope key, ability, expiry, origin or conversation), idempotency entries (key, request_id, result, expiry, durable?), the log (fields, redaction function inputs, retention job, export format, size cap), per-agent tokens (where kept, rotation record). The doc says the log is `oc.phonebridge.log.<profileId>` "registered with ProfileScope" (a prefs-style key) while reminders live in "the app's database". Which store, which schema, which migration, which writer lane? The native stores (`core/data`, `ProfileScopeTest`, WriterLane) have conventions; name the one used, and say how profile deletion removes: log, grants, reminders (and cancels armed alarms), tokens, and the agent config entries.

### R6. Registration is described per agent but not as a procedure - 2.2 table, "Version and compatibility checks"
Needed per agent: the exact file path inside the guest (given `PhoneAgentClaudeHome` per profile: what is the path resolved from the host side), the merge strategy (the user's existing `~/.claude.json`, `opencode.json` and `config.toml` contain other servers; the entry must be added without clobbering or reformatting; JSON/TOML/JSONC writers differ), atomic write, file permission mode, removal on revoke/uninstall, what happens on a malformed existing file, and how re-registration finds its own entry (name `phone` collides if the user already has a server called `phone`). Codex and Gemini rows are pure "Spike". For OC2 the `mcpAdd` signature in `Oc2Operations.kt` takes the entry; confirm the body shape the doc quotes (`type: remote`, `headers`, `oauth`, `codemode`) against the pinned OpenCode version, and the header secret form `{file:...}`: the file must exist before the call and its path must be guest-visible.

### R7. Confirm UI contract: which UI object, who renders, how the answer returns - 3.3, 5.2
The notification-then-sheet path needs: the PendingIntent target (trampoline activity like `ScheduleOpenActivity`?), what happens if the app is in the foreground on another screen (sheet host location), what happens with two pending confirms (stack, queue, replace), how a cancel (timeout, revoke) dismisses an open sheet, rotation/process-death restoration of an open sheet, and the Compose component API (the doc says "may be a new kit part", decision pending, plus G16 kit ratchet). Also missing: the exact sanitising function and the display algorithm for URLs (punycode conversion needs IDNA code; `Links.kt` does not have it; is there a KMP IDN library or a hand-rolled one?), and the data passed to the sheet (a sealed type of `ConfirmView` per ability).

### R8. Notification channel and copy specifics for the reminder - catalogue row 1, 3.3
"A reminder that rings" is undefined: channel id, importance, sound/vibration/alarm audio usage, whether it bypasses silent mode, lock-screen visibility, full-screen intent (Play-restricted on Android 14), snooze/dismiss actions, tap target, what happens if the channel is disabled. Also which API: `setExactAndAllowWhileIdle` (needs the permission; throttled idle) or `setAlarmClock` (no permission; mentioned in row 1 but not chosen). That is a design decision the implementer would have to make (and it changes the permission flow and the Play declaration); decide in the doc. The 3.4 sentence "may ring up to 10 minutes late" is not backed by any WorkManager guarantee.

### R9. Rate-limit, lock-out and time constants are all "first guesses" with no config location or test oracle - 3.2 table, T2, T5
Thresholds (64-character query, 500 ms, 5 per 10 min, 3 refusals, 5 wrong secrets/min) appear in prose and tables. The implementer needs: where they live (one `PhoneBridgePolicyConfig` with defaults), whether they are user-visible, the window type (fixed, sliding, token bucket), and the key (per conversation when unknown? then what), and how "paused until the person resumes from the transcript" persists across app restarts and what UI resumes it. "Refusals are sticky per conversation" (T1) vs "pause after 3 refusals" (3.2) vs "Don't ask again for this in this conversation" (3.4): three different rules; pick one.

### R10. MCP server implementation scope is not sized or decided - 2.2 "Version and compatibility checks", 4.1 item 2
"Serves both eras ... following the spec's own era detection" is a feature list, not a plan. Decide: hand-written minimal JSON-RPC over an embedded HTTP server (which library: Ktor CIO, NanoHTTPD, none of which is named; the repo's existing choices are not cited), SSE/streaming responses or plain JSON, which headers are required in each era, how `Mcp-Session-Id` is issued for legacy clients, behaviour for unknown methods and notifications, request size limit, concurrency model (the core is a serial lane, yet a confirm waits up to 5 minutes: tool calls from other agents must not block behind it, and `tools/list` must not wait). The serial-lane rule plus a 5-minute blocking confirm needs an explicit answer.

### R11. Idempotency specification contradicts itself and is not testable - section 4 vs 3.4 vs T7
Derived key "hash(profile, conversation-or-agent, ability, normalised arguments)" with a 24-hour replay returning the stored result will swallow legitimate repeats (see the Design Critic review). Also: what is "normalised arguments" per tool, where are results stored (durable? reminders yes, others unspecified), what does a repeat do when the first call is still waiting on a confirm (return the same pending result, or a second confirm?), and what does a client-supplied `request_id` collision with different arguments return? Provide the table.

### R12. Failure and permission handling lacks the code paths - 3.4, 4 "Mid-call permission revocation"
"The Android permission is checked right before acting, and SecurityException is caught and mapped." Which exceptions per adapter (exact-alarm `SecurityException`, camera `SecurityException`, `ActivityNotFoundException` for no browser/Custom Tabs provider, `FileNotFoundException`/quota for Downloads, Doze network)? Also native rule 5 says no `runCatching` around suspend code: the adapter result type (`Outcome`/`Failure` variants) is not named. List the failure variants the engine returns so the mapping table (3.4) is exhaustive.

### R13. Photo and file flows cross the process boundary with no size, format or transfer spec - catalogue rows 9 and 13, section 4 "Output limits", 5.2
"Returned as MCP image content, downscaled, or saved to a file and the path returned" is three options. For This phone v1: which one, max pixel size and quality, EXIF handling (GPS stripped?), where the file is saved (project folder: which, per conversation?), what path the guest sees, MIME allowlist for "pick one file", maximum size, how the picker is launched from a service (needs a foreground Activity; the notification-to-trampoline path), and what result the agent receives when the person cancels the picker. Camera capture has to use CameraX in an app Activity (the doc says so); the Activity contract with `android/camera` is not given.

### R14. Test plan lacks seams and acceptance values - 4.1
Names are promised (`B-BRIDGE-NNN`) but there is no list. Missing seams: fake clock (stated), fake Android adapters, fake agent client for the contract tests, a loopback test harness for the second APK probe, and a way to assert "no action without a matching confirm" (a spy adapter). The "pass rule" for the injection suite is good; add the oracle for each fixture (expected log entries, expected absence of adapter calls). The 4.1 item 3 "reminder rings while dozing" on an emulator needs the Doze control commands specified. Real-agent tests (item 4) require agent versions and credentials on the emulator; say which agent versions and who provides auth.

## Nit

- R15. Section 6 gives module names (`engine/phonebridge`, `android/phonebridge`, `feature/phonebridge`) but not their dependencies, the Gradle wiring, or who owns each (`MODULE_OWNERS` and the "shared modules stay with their owners" rule). Add a dependency table and the single-owner units touched (`android/agenthost`, `protocol/oc2`).
- R16. Words (5.4) are listed in English only; the Arabic strings and the ARB-equivalent words module path are not given. Fine for v1 draft, required before build.
- R17. D2/D3/D6 are decisions that change the core (which abilities, which grant classes, whether to set agent permissions to "allow"); the readiness gate should be: decisions made first, then the contract tables (R1, R3, R5), then build.
- R18. The estimate ("about 3 weeks ... plus a week of device QA") is a guess that the spikes can invalidate (R4, R6, R10). Mark it provisional or drop it.
- R19. Spike log (9) is desk research; the doc itself says "no code was run". The following must be verified in code before design freeze: OC2 `mcpAdd` body on the pinned version, Claude Code HTTP header form on the shipped version, Codex and Gemini keys, session hints, and the squatting behaviour of loopback ports on the target Android versions.
- R20. Acceptance criteria per ability ("done when ...") are absent; each v1 ability needs a one-line done condition tied to a test name.

## What is ready

- The risk classes and grant table (3.2) are precise enough to turn into a policy matrix test.
- The failure sentences (3.4) are close to usable copy, once mapped to error codes.
- The reuse inventory identifies real code to build on.
