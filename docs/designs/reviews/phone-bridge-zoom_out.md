# Phone bridge: Zoom Out goldfish review

Target: `docs/designs/phone-bridge-2026-11-09.md` (v1 draft, 498 lines). Mode: REVIEW. Reviewer: egm-zoom-out (Skeptical Architect). Question asked of every part: do we need it now, does the repo already have it, is it too deep in the weeds. Code searched under `native/` (read-only).

Verdict: the finish line is clear and the root problem (let an agent on this phone do a few phone things, behind an on-phone confirm) is real. The draft is too wide for a first slice and the doc spends many pages on v2/v3 and the Never list. Two reuse misses (reminders, confirm UI) could shrink v1 substantially. Security-critical simplifications are called out first.

## Blocker

### Z1. v1 carries eight abilities, a four-agent registration matrix, a two-era MCP server, a conversation-correlation engine and four grant levels, all before the confirm design is proven - Summary 9, section 6, 2.2, 3.2
The draft's own best argument is "the confirm on the phone is the safety line" and "open-URL tests the confirm design hardest" (section 6). A first slice that proves that line needs: one transport, one agent (OpenCode 2, which the app already registers MCP servers into through `mcpAdd`), the confirm sheet, the log, kill switch, and two abilities (open page, reminder). Everything else is breadth that multiplies the test matrix (8 abilities x 4 agents x 2 MCP eras x 4 grant classes) before there is evidence the confirm works. D2 option C (reminders, notify, open page) is the right size and should be the recommendation, not option A. Photo, Files, Share, Copy, Phone status can follow once the policy matrix is real.
Why it is a Blocker in simplicity terms: scope this wide will make the security core (the part the owner said "should be solid") the last thing finished, under schedule pressure.

## Major

### Z2. Reminders should reuse the schedules engine instead of a new reminder store and alarm path - catalogue row 1, section 4 "Reminders are durable data", "What exists today"
The repo already has `engine/schedules` (`ScheduleStore`, `ScheduleEngine`, `ScheduleClaims`, `Recurrences`, `ScheduleTime`, `ScheduledOpen`) and `android/schedules` (`ScheduleExactAlarms`, a boot/update/time/zone/exact-alarm re-arm receiver, `ScheduleOpenActivity`) which already does: durable rows, exact alarm with WorkManager fallback, re-arm on BOOT, MY_PACKAGE_REPLACED, TIME_SET, TIMEZONE_CHANGED and the permission-state broadcast, per-profile scope, and a notification tap route. The draft lists the receiver pattern as "reuse" but then specifies a second durable store ("id, text, due time, zone, created-by..."), a second re-arm list (section 3.3 repeats the receiver's intent filters), and new list/cancel tools. Extend the schedules model with a "reminder" kind (notify at time, no prompt run) rather than building a parallel reminder subsystem. This removes two of the four "plumbing" items (store, re-arm) and a class of drift bugs (two alarm receivers, two exact-alarm permission paths).
Related: the FactsBook reminders (decision D4) is another reminder store; D4 option C ties three together. Pick one store and say so.

### Z3. The confirm and grant machinery probably already exists in `engine/requests/consent` - sections 3.2, 5.2
`engine/requests/consent` has `ApprovalModes`, `AutomationPolicy`, `AlwaysAllowInvitation` and `PermissionInvitationAuthority`, and `engine/requests/ask` has `PermissionAsk` and `PermissionTitle`: the app already has a model of "an agent asks, the person allows once / always / rejects" with titles and policy. The draft invents a new `engine/phonebridge` core with "grants, rate limits, idempotency and the log" and a new confirm sheet without comparing against it. Required before v2: a short mapping of the new Allow-once / Allow-for-conversation / Never-always model to the existing consent types and what is genuinely missing (probably only the per-conversation scope, expiry and rate limits). Also search the kit for an existing confirm sheet (KitSheet exists in `ui/kit/modal`); the draft says "the confirm sheet may be a new kit part". Decide against the kit catalogue first.

### Z4. The transport choice is a security decision, not a convenience - 2.2 (UDS "considered and parked")
Reuse and simplicity point at HTTP on loopback because agents speak it natively, which is the right instinct for adoption. But the dismissal of Unix sockets rests on a threat (code inside the guest) that the design says it cannot stop anyway; it ignores the one it can (other Android apps, T4). Zoom out: the simplest design that is also safe is the one where only the guest can reach the bridge. Compare costs honestly (a tiny per-ABI shim versus a port other apps can squat and harvest secrets from). See the Design Critic review, B1. Do not let "no extra binary" settle a security question.

### Z5. The remote story (2.3, five options table) is speculative design for a non-goal - Summary 3, 2.3, section 6 v2
Five transport options for v2, an elaborate background-limit discussion, and a comparison table with OpenCode/Claude Code (2.4) are written for features the draft itself says are not in v1 and need a one-day spike first. YAGNI: keep one paragraph ("remote needs a reverse channel; spike later; no queue") and move the options table into the spike's own doc. The same applies to the row-by-row cataloguing of v3 items (6b-6d, location, speech) and to the 21-row catalogue's "Never" entries (rows 12, 16, 17b, 18, 21), which belong in a one-paragraph Never list (the doc already has one in section 6). Keep the accessibility-service argument (1.2) in a sentence or two; it repeats Play policy that matters only if someone asks for it again.

### Z6. Premature mechanisms in v1: derived idempotency keys, pause-after-3-refusals, 11-row rate-limit tables, `notifications/tools/list_changed` - 2.1, 3.2, 4
Each has a cost (state, UX, tests) and none is tied to an observed problem. Derived idempotency keys also create a correctness bug (identical legitimate repeats are swallowed; see Design Critic M3). Prefer: `request_id` idempotency only for reminders (the DB constraint), a single global cap per ability per conversation, and "tool list changes are picked up on the agent's next session". `list_changed` support varies across the four agents; sending it is cheap, but relying on it in the UX is not.

### Z7. Dynamic tool listing plus `phone_abilities` meta tool plus in-transcript "Turn on" actions: three mechanisms for "ability is off" - 2.1, 5.1, 3.4
The draft lists tools only for abilities that are on, adds a meta tool so the agent can tell the person what to enable, and adds a transcript action. One of these is enough. Simplest: always list all v1 tools, return the plain "Reminders are off, turn them on in Settings > Phone abilities" error when off (3.4 already specifies the wording), and let the existing tool-step rendering carry a "Turn on" action. That removes `list_changed`, the meta tool, and the "tool disappears from the agent's list mid-conversation" behaviour that confuses models.

## Nit

- Z8. "What exists today" is a good inventory, but several rows are reuse in name only: `AppFunctions` (other direction, Flutter branch, not merged), JobFinder (v3), `PhoneAgentClaudeHome` (needed only if Claude Code is in v1). Mark each row as v1 reuse or not.
- Z9. Altitude: sections 2.2 and 2.4 drop into config-key level (header names, env var names, `{file:...}` forms) for four agents, two of which are explicitly unspiked (Codex, Gemini). Keep the architecture ("the app writes one entry per agent in that agent's config") and park the keys until the spike; most of them will be wrong when it runs.
- Z10. Section 4.1 test plan: 8 adversarial fixtures plus real agents on an emulator for every ability is thorough but each of the 4 agents multiplies it. Say which tests run against which agent; run the injection suite against the policy core with fakes first, and run live agents only for registration and one call each.
- Z11. The finish line says an agent can "ask for a photo or a file". The ask-for-photo journey (agent calls, sheet opens in a backgrounded app, camera, return) is the most complex flow in v1 (background activity start rules, camera lifecycle, EXIF, size limits) for a value the owner did not name. Candidate to cut.
- Z12. Words (5.4), the Quick Settings tile, an action on the server notification and the Settings page are four revoke/enable surfaces. D8 recommends all three kill-switch homes. A Settings switch plus the existing notification action is enough for v1; the tile can follow (the doc itself notes `android/tiles` exists, so the tile is cheap, but each surface is a test and a string).

## Root-problem check

The doc answers the right question (agent-to-phone abilities behind a trustworthy confirm). It drifts when it tries to also answer: how do remote agents reach the phone, what is the right browser story, and what is the ideal assistant integration. Cut those back to one-paragraph notes and let v1 prove the confirm and the transport on two abilities.
