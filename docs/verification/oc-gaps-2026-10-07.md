## List questions

Finish line: show and answer/reject pending questions from an unopened list row
using its exact profile and directory. Non-goals: opening/resuming chats,
changing selected location, or reading/subscribing to session history.

Implemented independent directory-scoped inventories for waiting rows, integrated
with the existing list refresh. Each connection reads at most four directories
per pass, rotating across larger sets; each endpoint has a three-second timeout
(two reads per directory, at most 24 seconds of question reads). Only directories
with `needsYou` rows are read. Up to 128 results per endpoint are inspected and
only requests matching a row in that directory are retained (at most 256
merged requests per directory). Excluded or failed
coverage is not actionable. Nothing from this cache is persisted.

The legacy and modern question surfaces are merged while preserving endpoint
provenance. Replies use a fresh pair scoped to the captured profile and directory;
modern replies also carry the captured session ID. Profile identity is detached
from mutable saved-profile objects. Existing captured request identities and
`_withPendingReply` remain in use. Repeated taps share a send; an uncertain send
is not automatically retried or routed to another endpoint. Equivalent refreshes
retain the attempted marker. Replacement, failed reads, removal, profile changes,
profile deletion admission, disconnect and disposal invalidate old snapshots.

Global request events immediately invalidate affected inventories and schedule
refetch through the existing debounce. A trailing refresh preserves events that
arrive during an older read. The side-server test no longer opens the chat to
prepare the location. Existing inline choices, Undo and sheets use the same UI.

### Protocol scope requiring coordinator attention

The current `ProfileMonitor.readQuestions` contract is **OC1 legacy plus OC1's
modern `/v2` question API**. These are the two paths tested here. The actual
pinned **OC2 beta replaces questions with typed forms**: its
`Api2Gateway.pendingQuestionsV2` returns an empty list and question reply methods
are deliberately unavailable. See `docs/opencode2-protocol-notes.md` §8 and
`lib/api2/gateway.dart`. Do not report the synthetic modern question test as an
OC2 beta end-to-end test. Typed-form list presentation needs its own preserved
form schema/reply contract and Claude's UI integration; no lossy conversion to
`List<List<String>>` was added. Clarification was requested during this run.

## Reopening a newly created Claude conversation

Finish line: returning from Conversations attaches to the existing Claude
agent, loads its history and exposes its pending permission; any remaining
history error names Claude's helper instead of OpenCode. Non-goals: resuming
an already-live agent, creating a replacement conversation, retrying a prompt,
changing a permission decision, restarting the app/helper, or device mutations.

Root cause: the feed gateway keeps a new conversation's local draft UUID and
maps it to the daemon agent ID after `create_agent_response`. Initial chat
creation already returns the daemon ID. Reopening a live row passed the local
UUID to the independent chat gateway, which has no such private mapping. Its
first `fetch_agent_request` therefore asks for an unknown agent; the daemon's
RPC failure becomes `PaseoFailureKind.unavailable` and ChatScreen's history-load
error. Waiting status does not require a resume. The regression also reproduces
for an idle conversation created through that same draft path, so the reported
working idle rows do not establish that busy state itself causes the failure.

`openChatFeedItem` now translates through the exact row source gateway before
setting the backend owner, title or chat route. The live feed retains its local
identity, preserving captured list permission/question actions. Saved row copies
also use daemon IDs (including parent IDs), because a private alias cannot
survive a restart. The existing saved-row format is unchanged; old unresolvable
aliases are replaced by fresh directory inventory, never matched by title or
guessed to be a different session.

The four reopen regressions cover running and idle snapshots with a pending
shell permission, with and without disposing the original chat backend. They
load history through the independent backend, hydrate and answer the original
request, and assert no resume/create/send mutation on reopen. A fifth regression
checks that the saved row and preview hold the daemon ID rather than the local
UUID. The failure-copy regression retains Retry/Details while using existing
localized `agentNotAnsweringPhone` copy for agent backends; no ARB or generated
localization changes are needed.

Read-only device evidence: the supplied `daemon.log` contained supervisor
lifecycle events but no request failure. Worker logs go to that same file;
existing setup config sets them to `fatal`, so ordinary RPC errors were not
recorded. Filtered Flutter logcat likewise did not identify a failed Paseo RPC.
No verbosity was changed and no replacement daemon was run. The failing request
is confirmed by the source path and the scripted RPC reproduction, not claimed
as a captured device RPC. The user was asked to leave the pending request alone,
return to Conversations and tap its row once for a fresh capture.

## Photo answers from Agent cards (Paseo)

Finish line: a photo answer from a newly created Claude conversation reaches
that same daemon agent with its image bytes, settles the card from transcript
evidence, and cannot be resent through the list after uncertain delivery.
Non-goals: changing the photo picker, attachment storage, permission policy,
retrying any previously uncertain answer, or device mutation.

The composer and card already use the same `paseoImages` attachment encoder.
The failing difference is gateway identity. The card sends through the stable
feed gateway, which retains a local draft ID for a conversation it created;
the chat card carries the daemon ID. `_promptAsync` looked up that daemon ID in
local-keyed inventory, then `_fetchAgent` stored its result under the local ID.
The subsequent provider lookup failed with `unavailable` before the transport's
send fence. `PromptTrace.sent` precedes this lookup, so `mark prompt.sent` does
not establish that a wire message was sent. This reproduces the reported symptom
without changing or dropping image bytes.

Paseo prompt and card-idle checks now normalize to their gateway's local ID
before inventory, pending-turn, active-turn and uncertainty checks; the wire
request still uses the exact daemon ID. The connection's card boundaries use
the daemon ID from the exact profile/source/directory gateway, giving chat and
list one card identity, Undo operation, dispatch journal and settlement state.
Bounded history reads preserve the requested canonical ID. No chat resume,
replacement agent, attachment persistence or automatic retry is added.

Older local-ID dispatch records remain intact. A matching message/call in the
same full scope blocks a new answer even when that old session alias can no
longer be resolved after restart. This deliberately stays conservative if an
old uncertain answer cannot be reconciled. Deletion events carry the daemon ID
captured before the gateway forgets its alias; both old/local and canonical card
state are removed. Explicit deletion through the chat backend is also covered
without a remote deletion event. No UI files changed for this fix.
